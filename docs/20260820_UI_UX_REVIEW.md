# UI/UXデザインレビュー(Claude) — タイムライン中心レビュー

- 文書種別: レビュー記録
- レビュー実施日: 2026-08-20
- レビュー対象: `public/index.html`, `public/styles.css`, `public/app.js`, `server.js`, `README.md`
- レビュー方式: `node server.js` でローカルサーバーを起動し、ヘッドレスChrome(Chrome DevTools Protocol経由)で実画面を操作・スクリーンショット取得。あわせて競合ベンチマークとしてOllo Factory Tools公式ページ(https://ollo.jp/ollo-factory/tools, https://ollo.jp/en/ollo-factory/tools)を取得・比較。コード変更は行っていない(レビューのみ)。
- 想定運用条件(このレビュー後に判明): 実際に扱う動画は**20分程度**になる見込み。現行サンプルは30秒・4区間のみで、この長さでは後述P0課題が顕在化しない。

このファイルは実装を変更しない。指摘事項の記録のみを目的とする。

---

## 1. 総評

**完成度**: MVPとしての作り込みは高水準。初期状態→サンプル設定→解析確認ダイアログ→解析中→完了→中止→区間選択→編集→追加削除→Undo/Redo→AI予測切替→未保存バッジ→JSON保存、の一連の操作を実機で確認したが、JSエラーは発生せず(コンソールはfavicon 404のみ)、破壊的操作(区間削除、新規解析による上書き)には必ず確認ダイアログが挟まる。

**Ollo Factory Toolsとの比較**: Ollo公式ページ(日本語・英語とも)は「動画から即座に工程を判別しガントチャートで作業時間を可視化」等のテキストと汎用アイコン(矢印分岐・ストップウォッチ・原子マーク・再生ボタン)のみで、実画面のスクリーンショットは非公開。そのため画面レイアウト・色の意味・現在位置表示・選択表示・短区間/多数区間対応・編集/閲覧モードの区別は**すべて未確認**。機能面では「複数人作業分析」「ムダ作業抽出」「改善案提案」等、単一作業者の区間ラベリングを超えた分析機能がOllo側に明記されているが、本アプリはそもそも単一動画・単一作業者の区間確認/修正UIの検証が目的であり、単純比較はできない。

**次のデモに出せるか**: 30秒・4区間サンプルの範囲では問題ない。ただし実際の動画(20分程度)を使う検証に進む前に、P0課題(短区間のタイムライン番号消失)を必ず解消すること。この課題はサンプルデータでは再現しない「隠れたブロッカー」。

---

## 2. 課題一覧(重要度順)

### 課題1 — 短い区間がタイムライン上で無地の箱になり番号が消える
- **優先度**: P0
- **画面箇所**: 動画と作業タイムライン(区間バー)
- **根拠**: `public/app.js:309` の `width < 7` 判定(`width`はタイムライン全体幅に対する%)と `public/styles.css:665` `.segment-block.short .segment-label { display: none; }`。実機検証で区間を削除し00:00:09〜00:00:11(2秒/全体30秒=6.7%)の区間を追加したところ、タイムライン上は番号なしの無地ブロックになった。
- **問題**: 「短い」の判定が**動画全体長に対する割合(7%)**。30秒動画では7%≒2秒だが、**20分(1200秒)動画では7%≒84秒**。実際のTAS(時間動作研究)の作業要素はしばしば数秒〜数十秒単位であり、20分動画では大多数の区間が番号非表示になる可能性が高い。
- **現場利用者への影響**: タイムライン上で区間を番号で追えず、隣接区間を取り違えて編集・削除するリスク。一覧とタイムラインの目視照合効率が大きく低下。
- **改善案**: 「短い」の判定を動画全体比率ではなく、**タイムライン上の実ピクセル幅**(例: 24px未満)で行う。番号が入らない場合も、外側に極小の連番タブを出すなど代替の識別手段を用意する。
- **実装難易度**: 中(閾値ロジックと代替表示の設計)
- **受入確認方法**: 20分・多数区間(30〜60区間、区間長5〜30秒混在)のサンプルデータで、タイムライン上の全区間の番号(または代替の識別要素)が視認できることを確認する。

### 課題2 — ドラッグで境界移動が隣接区間に阻まれた際、無反応でフィードバックがない
- **優先度**: P1
- **画面箇所**: タイムラインの区間境界ドラッグハンドル
- **根拠**: `public/app.js:335-340` の `boundaryLimits()` が隣接区間の境界でクランプする。実機で区間の開始ハンドルを隣接区間側へドラッグしたが、位置が全く変化しなかった(スクリーンショット比較で確認)。一方キーボード操作(矢印キー)の `nudgeHandle()`(`app.js:347-355`)は移動できない場合に「隣の区間または動画端を越えて移動できません」というトーストを出すが、ポインタドラッグの `beginHandleDrag` の `move` 処理(`app.js:356-369`)には同等の通知がない。
- **問題**: マウス/タッチ操作時のみフィードバックが欠落しており、キーボード操作と非対称。
- **現場利用者への影響**: 「操作方法が間違っているのか、アプリが固まっているのか」を判断できず、無駄な試行錯誤が発生する。
- **改善案**: ドラッグがクランプされた瞬間(値が前回と同じになった時)にも、キーボード操作と同じトーストまたは軽量な視覚フィードバックを出す。
- **実装難易度**: 小(`beginHandleDrag`のmove内に差分判定とtoast呼び出しを追加)
- **受入確認方法**: 隙間なく隣接する2区間の境界を限界方向へドラッグし、視覚的フィードバックが出ることを確認する。

### 課題3 — タイムラインに色・記号の意味を示す凡例がない
- **優先度**: P1
- **画面箇所**: タイムライン全体
- **根拠**: `public/index.html:84` の `timelineHint` は操作方法(クリック/矢印キー/両端ドラッグ)のみを説明し、色の意味(選択中=黄緑の上辺、現在位置=赤い縦線、要確認=一覧側の黄色下線)を説明する凡例がタイムライン付近に存在しない。
- **問題**: 「色に作業分類の意味を持たせない」設計方針自体は妥当だが、代わりに使っている「選択中/現在位置/警告」という視覚言語の意味がどこにも明文化されていない。
- **現場利用者への影響**: 初見の現場リーダーが赤い縦線と黄緑の上辺の違いを自力で正しく解釈できる保証がない。
- **改善案**: タイムライン下のヒント行に「■選択中(黄緑の上辺) ┃現在位置(赤い縦線)」のような最小限の凡例を1行追加する。
- **実装難易度**: 小(`index.html`のヒント文言に凡例を追加)
- **受入確認方法**: 初見のユーザーに画面を見せ、「選択中の区間」「現在の再生位置」をそれぞれ指差してもらうユーザビリティテストを実施する。

### 課題4 — 警告(要確認)のある区間がタイムラインに一切反映されない
- **優先度**: P1
- **画面箇所**: タイムラインの区間ブロック
- **根拠**: `renderTimeline()`(`public/app.js:303-334`)は `state.warnings` を一切参照していない。警告の可視化は `renderList()`(`app.js:373-393`)側の `.segment-row.warning::after`(`styles.css:843-851`、下端2pxの黄色線)のみで行われている。
- **問題**: 時刻不正・重複などの警告は一覧をスクロールしないと気づけず、タイムライン上でどの区間が問題を抱えているか一目で分からない。
- **現場利用者への影響**: 区間数が多い場合(20分動画では特に)、警告のある区間を見落とす可能性が高い。タイムラインだけを見て作業しているリーダーには警告が届かない。
- **改善案**: 警告のある区間のブロックに、選択中(上辺)・現在位置(縦線)と衝突しない位置(例: 下端に薄い黄色の線)で警告を反映する。
- **実装難易度**: 小〜中(`renderTimeline`内で`state.warnings[index]`を見てクラスを付与)
- **受入確認方法**: 重複する時刻に区間を編集し、タイムライン側だけを見て問題箇所を指摘できるか確認する。

### 課題5 — `--current` と `--danger` のCSSトークンが同一値
- **優先度**: P2
- **画面箇所**: `public/styles.css:16-17`
- **根拠**: `--current: #ff6b6b;` と `--danger: #ff6b6b;` が同一値で定義されている。
- **問題**: 「現在位置」と「危険操作」が意味的に結合しており、将来どちらかの色だけを変更しようとすると意図せず他方にも影響する。
- **現場利用者への影響**: 直接の実害は小さいが、赤=現在位置という表現が「問題がある場所」という誤読を招く可能性がある。
- **改善案**: `--current` を独立トークンとして定義し直す(色自体は据え置きでよい)。
- **実装難易度**: 小
- **受入確認方法**: CSS差分レビューのみ。

### 課題6 — モバイル幅でのドラッグハンドルの当たり判定が横方向に狭い(未確認)
- **優先度**: P2
- **画面箇所**: タイムラインのドラッグハンドル(モバイル幅)
- **根拠**: `styles.css:667-679` でハンドルは幅28px×高さ44pxと定義。420px幅の実機描画でも同寸法が適用される。
- **問題**: 高さ44pxはタッチターゲットの目安を満たすが、横方向の当たり判定が28pxとやや狭い。**実機タッチ操作での検証は未実施、未確認。**
- **改善案**: モバイル幅時のみヒット領域を広げる、またはタップ式ステッパーUIを併設する。
- **実装難易度**: 中
- **受入確認方法**: 実タブレット端末でハンドルをドラッグし、意図した秒数で止められるかテストする。

### 課題7 — 解析中の進捗表示に定量的な目安がない
- **優先度**: P2
- **画面箇所**: 解析状態カード(解析中)
- **根拠**: `beginProgress()`(`app.js:132-140`)は経過時間とステージ名のテキストのみで、パーセンテージやプログレスバーはない。
- **問題**: モックモードでは数秒で終わるため問題にならないが、実APIモードで処理が長引いた場合、あとどれくらい待てば良いか分からない。20分動画を扱う場合、実API解析時間が長くなる可能性があり影響が増す。
- **改善案**: 目安時間を`statusMessage`に添えるか、簡易な不定進捗バーを追加する。
- **実装難易度**: 小
- **受入確認方法**: 実APIモードで解析を実行し、待機中の表示が違和感を与えないか確認する。

## 3. タイムラインのデザイン評価(要点)

**良い点**: 区間色の単一化(`app.js:2-4`)、暗い隙間による境界表現(`styles.css:634`の`border-right`)、選択中(横線)/現在位置(縦線)の形状差別化、キーボードフォーカス時の高コントラストな黄緑アウトライン(実機確認済み)は維持すべき設計。

**最大の懸念**: 「短い」の判定が動画全体比率(7%)であるため、**20分動画では大多数の区間が番号非表示になる**(課題1)。これは今回の想定運用条件(20分動画)が判明したことで、優先度がP0で確定した。

**その他**: 色の凡例なし(課題3)、警告のタイムライン非反映(課題4)、ドラッグクランプ時のフィードバック欠落(課題2)。

---

## 4. 結論

- **次のデモに出してよいか**: 30秒サンプルの範囲では可。20分動画での本番検証に進む前に課題1(P0)は必須修正。
- **最低限直すべき項目**: 課題1(P0)、課題2・3・4(P1)。
- **後回しでよい項目**: 課題5・6・7(P2)。
- **次のデザイン改善フェーズで最初に行うべきこと**: 20分・多数区間(30〜60区間程度、区間長5〜30秒混在)のダミーデータでタイムラインを再検証し、課題1の改善効果を確認する。
