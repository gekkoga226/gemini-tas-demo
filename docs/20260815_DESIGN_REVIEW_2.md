## 1. 総評

**結論: 条件付き完了可。必須修正1件（M1）を反映すれば設計フェーズを閉じてよい。**

前回レビューの必須修正M1〜M4と推奨修正R1〜R10は、いずれも実質的に反映されている。形式だけの追記ではなく、指摘の根拠まで踏まえて本文へ織り込まれており、特に次の3点は前回の懸念が解消したと判断する。

- **入力上限の事前判定**（DESIGN 3.3・6.1・7.1・8.1）: 容量ではなく再生時間が支配要因であるという整理が本文に入り、`ceil(動画秒数) × 300 + ページ数 × 258 + プロンプト分` という概算式と、100%以上は送信前拒否・80%以上は警告という閾値が具体化された。U1の2GB上限（2GBかつ57分なら約4.7 Mbps相当）と概算式の実効上限が現実的な範囲で両立している点も確認した。

## 3. 必須修正

### M1. 入力ゲートの判定入力（PDFページ数・動画再生時間）が「取得できた範囲で」となっており、同じ節の必須判定と矛盾する

- **対象ファイル・節番号**: `docs/DESIGN.md` 6.1節（あわせて5.1・5.2・7.2節）
- **根拠**:
  DESIGN 6.1は2つの箇条書きが隣接している。

  > - ファイル名、容量、動画時間、PDFページ数を**取得できた範囲で**表示する。
  > - 動画時間、PDFページ数、固定プロンプト分から概算入力トークンとcontext上限に対する割合を表示する。80%以上は「上限に近い」と警告し、100%以上は解析開始を無効にする。

  後者はページ数と動画時間が**必ず取得できていること**を前提にした強制ゲートである。さらにDESIGN 3.4の入力前確認手順4と7.2は「1,000ページ超は解析前にエラーにする」と定めており、これもページ数の取得を必須とする。前者の「取得できた範囲で」は、ページ数が取得できない場合を許容する表現であり、その場合に概算判定と1,000ページ判定をどう扱うのかが定義されていない。

  加えて、ページ数の取得主体が定義されていない。動画長については前回R1の指摘を受けてDESIGN 10.3が「ブラウザが `loadedmetadata` で取得した小数秒の動画長を解析要求時にローカル処理サービスへ渡す」と明記したが、PDFページ数には同等の記述がない。DESIGN 5.1（ブラウザ＝ファイル選択と基本検証）と5.2（サービス＝入力を一時領域へストリーム保存）のどちらが解析するかが読み取れず、6.1の解析前表示に使う以上ブラウザ側で必要になるが、7.2のエラー判定はサービス側でも行われうる。

- **影響**:
  - ページ数が取得できないPDF（構造が特殊、部分的に破損、ページツリーが非標準など）を選んだとき、解析開始を許すのか拒否するのかが実装者判断になる。許した場合、概算入力チェックを迂回して送信され、context超過による `incomplete` を数十分後に受けることになる。これはM2（前回）で潰したはずの失敗経路が別ルートで復活することを意味する。
  - 1,000ページ判定も同時に迂回される。SPEC 7.3の「ページ数だけを理由に拒否しない」は守られるが、公式上限超過を送信前に止めるというDESIGN 3.4の設計意図が崩れる。
  - 取得主体が未定義なため、ブラウザ側とサービス側で異なるページ数を用いる実装差が生じうる（動画長は10.3で統一済みなのに、ページ数だけ統一規則がない）。

- **修正案**（DESIGN 6.1と7.2へ次の趣旨を追記する。文言は設計書の文体に合わせて調整してよい）:
  1. 6.1の1つ目の箇条書きを「ファイル名と容量は常に表示する。**動画再生時間とPDFページ数は解析開始の必須条件**とし、取得できた値を表示する」に改める。
  2. 「動画再生時間またはPDFページ数を取得できない場合は、入力エラーとして扱い、解析開始を有効にしない。PDFについては破損・暗号化と同じ分類で案内する」を6.1または7.2へ追加する。
  3. 10.3の動画長と同様に取得主体を定義する。推奨は「PDFページ数はブラウザ側で取得し、解析要求時にローカル処理サービスへ渡す。サービス側は受領した値で1,000ページ判定と概算入力判定を再確認する」。ブラウザ側で取得しない方式を採る場合は、6.1の解析前表示をサービスからの応答で行う旨を明記する。
  4. 13.1のエラー分類表「入力」行の例に「ページ数・再生時間を取得できない」を追加する。

- **設計フェーズ完了への影響**: これ以外に設計フェーズを閉じることを妨げる未解決事項は見当たらない。本項の反映をもって完了可と判断してよい。

## 4. 推奨修正

いずれも設計フェーズの完了を妨げない。R1〜R3は実装着手前の小規模疎通（SPEC 18.1）に加えると費用対効果が高い。

### R1. JSON Schemaの内容と、スキーマ拒否時の扱いが未定義

- **対象**: `docs/DESIGN.md` 8.2節、`docs/SPEC.md` 18.1節
- **根拠**: DESIGN 8.2は `response_format` に「正式9項目の配列を表すJSON Schema」を設定するとだけ書いており、スキーマ本体の内容（9項目のtype、requiredの指定範囲、配列のitems定義、`pattern` 等の追加制約を使うか）が定義されていない。公式は "supports a subset of the JSON Schema specification"、"Very large or deeply nested schemas may be rejected" と明記しており、**スキーマが受理されない可能性がAPI側に存在する**。U3で既定ONと決まった以上、受理されなければ全解析が開始できない。
- **影響**: スキーマ非受理時にどう振る舞うか（画面外設定と同じ経路で自動的に無効化して続行するのか、設定エラーとして停止するのか）が未定義。実装後に判明すると、既定ONという確定事項の再検討が必要になる。またU5の厳密な `HH:MM:SS` 検証との関係で、スキーマ側に時刻の書式制約を入れるか否かで、A違反による全体不採用の発生率が変わる。
- **修正案**:
  1. 8.2に「使用するJSON Schemaの構成」を明記する。推奨は、配列 + 9プロパティすべてrequired、`duration_seconds` のみ整数、他8項目は文字列、追加キーワードは使わない最小構成。`pattern` による時刻書式の強制は、サポート状況が確認できるまで採用しない（採用可否は小規模疎通で確認）。
  2. 「スキーマがAPIに受理されない場合は設定エラーとして扱い、無断で無効化して解析を続行しない」を8.2または13.1へ追加する。
  3. SPEC 18.1のチェック項目に「`response_format` に指定するJSON Schemaが受理されること」を追加する。**動画・PDFを送らずに短いテキスト要求で確認できる**ため、U2の「実装前は小規模疎通のみ」という制約に抵触しない。

### R2. `max_output_tokens` の初期値65,536に根拠がなく、上限確認のゲートがない

- **対象**: `docs/DESIGN.md` 8.2節、`docs/SPEC.md` 18.1節
- **根拠**: DESIGN 8.2は「初期値65,536。ただし設定モデルの公式最大値を超えない値を明示指定」としているが、3候補モデルそれぞれの公式最大値は本書でも公式一覧の引用でも確認されていない。モデル上限を超える値を指定すれば通常400系エラーとなり、解析が一切開始できない。
- **影響**: 暫定モデル `gemini-3.1-pro-preview` の上限が65,536未満だった場合、実装直後に全解析が失敗する。U4で初期採用モデルを実装後に切り替える方針であるため、モデルごとに上限が異なると切替時に同じ失敗が再発する。
- **修正案**:
  1. 8.2の表に「候補モデルごとの公式最大出力トークン数を確認し、`min(65536, モデル公式最大値)` を設定する」と明記する。
  2. SPEC 18.1へ「候補モデルごとの `max_output_tokens` 上限値の確認」を追加する。R1と同様、テキスト1件で確認でき、動画・PDFの送信を伴わない。
  3. モデル切替（`GEMINI_MODEL` 変更）時に上限超過設定のまま起動しないよう、起動時に値の妥当性を検査する旨を8.2または14章へ1行加える。

### R3. 概算入力トークンに使う「検証済みプロンプト分」の初期値が未定義

- **対象**: `docs/DESIGN.md` 3.3節
- **根拠**: DESIGN 3.3は「検証済みプロンプト分は固定値として画面外設定に保持し、許可後のAPI事前確認で同一モデルの値へ更新する」としているが、更新前の初期値が示されていない。概算式は解析開始ゲート（100%で送信前拒否、80%で警告）の入力であるため、値が未定のままでは判定が定義されない。
- **影響**: 実務上の影響は小さい。`reference/validated_prompt.md` は約2.4KBであり、日本語混じりでも概ね1,000〜1,500トークン規模と見込まれ、1,048,576に対して0.15%程度にすぎない。ただし「設計値が未定のまま実装へ渡る項目」が1つ残ること自体が、設計フェーズを閉じる際の瑕疵になる。
- **修正案**: 3.3に「初期値は安全側に2,000トークンとし、小規模疎通で `countTokens` 相当の手段が使える場合は実測値へ更新する。プロンプト分はcontext上限の0.2%未満であり、概算判定の結論を左右しない」と明記する。あわせてSPEC 18.1へ「検証済みプロンプトの実トークン数の確認（テキストのみ、動画・PDF不要）」を追加してもよい。

### R4. SPECに「設計フェーズで検討／判断する」という先送り表現が2か所残存

- **対象**: `docs/SPEC.md` 9.1節、11.1節
- **根拠**:
  - SPEC 9.1: 「障害調査のために生の応答を一時的に保持する必要性や方法は、設計フェーズで検討する。」→ DESIGN 8.3で決定済み（`GEMINI_DEBUG_DUMP=1`、既定OFF、限定一時領域、APIキーと認証ヘッダーを含めない、終了時と次回起動時に削除）。
  - SPEC 11.1: 「動画最大時間の上限値、またはタイムラインの拡大表示機能の要否は、設計フェーズで動画長の上限確定と合わせて判断する。」→ DESIGN 3.3・7.1で「固定の最大時間は設けず概算式で判定」、DESIGN 11.3で「MVPでは拡大機能を必須にしない」と決定済み。
- **影響**: 内容の矛盾ではなく、状態表示の齟齬である。SPEC 18章を「未決事項」から「確認ゲート」へ書き換えて設計フェーズを閉じる文書構成にした一方で、本文2か所が設計フェーズ待ちのまま残っているため、第三者が読むと未決事項が残っているように見える。SPEC 19章の終了条件「確定要件、受入条件、実装・受入に向けた確認ゲートが明記されている」との整合も損なう。
- **修正案**: SPECを更新する場合は、9.1を「障害調査用の生応答の一時保持は、既定OFFの画面外設定でのみ有効化できる方式とする（詳細は設計書8.3）」、11.1を「MVPではタイムラインの拡大表示機能を必須とせず、1秒単位の確定は数値入力で行う。動画長は固定の最大時間ではなく入力トークンの事前判定で制御する（詳細は設計書3.3・11.3）」に改める。SPECを変更しない方針であれば、DESIGN 2章のSPEC対応表へ「SPEC 9.1・11.1の設計フェーズ判断事項は本書8.3・3.3・11.3で決定済み」という行を追加するだけでもよい。**SPEC本文の変更はユーザー承認が必要なため、独断では行わないこと。**

### R5. `ceil(実動画長)` を許容上限とする規則が、SPEC 17.5の受入判定と衝突して見える

- **対象**: `docs/DESIGN.md` 10.3節、`docs/SPEC.md` 9.4 B・17.5節
- **根拠**: DESIGN 10.3は「整数秒で表せない末尾を失わないため、許容する最大 `end_time` は `ceil(実動画長)` 秒とする」と定めた。一方SPEC 9.4 Bは「区間は動画の0秒より前または動画終了後に出ないこと」、SPEC 17.5の受入条件は「動画の終了時刻を超える位置へ区間を移動する編集は確定できない」である。動画長が100.4秒のとき、DESIGNは `end_time = 00:01:41`（101秒）を許容するが、これは実動画長を0.6秒超えている。
- **影響**: 設計としては妥当（半開区間で末尾0.4秒を表現するには101秒が必要）だが、受入試験でこの1件だけを見た担当者が「動画終了後の区間が確定できてしまう」としてNG判定する可能性がある。設計の正しさではなく、判定基準の伝達の問題である。
- **修正案**: DESIGN 10.3へ「SPEC 17.5の受入判定は `ceil(実動画長)` を動画終端とみなして行う。`ceil(実動画長)` を超える値は確定できない」と明記する。受入試験手順を別途作る場合は、そこにも同じ注記を入れる。ユーザーがこの解釈を明示的に確認しておくとなお良い（後述5章）。

### R6. Gemini上の一時ファイルとinteraction ID記録の削除タイミングが、終端状態すべてを覆っていない

- **対象**: `docs/DESIGN.md` 3.5節、5.3節、8.1節、13.2節
- **根拠**:
  - DESIGN 3.5は「解析完了・中止・失敗時にアプリから削除を試み」とあり、3.6で定義した終端状態のうち `requires_action`・`incomplete`・`budget_exceeded` が文言上どれに該当するかが明示されていない。8.1のシーケンス手順11も `completed` 経路にしか現れない。
  - DESIGN 5.3は「実行中のinteraction IDだけを…保存する」「再起動時は未終了IDのcancelと記録削除を試みる」と定めるが、**正常終端時に記録を削除する**という記述が13.2にも8.1にもない。読み手には暗黙に伝わるが、明文化されていない。
- **影響**: 実害は小さい。前者は最大48時間でGemini側が自動削除するため上限が決まっている。後者は、記録が残ったまま再起動すると完了済みinteractionへcancelを送ることになり、無害だが不要なAPI呼出しとログノイズになる。

### R7. 対応ブラウザ方針の「実施時期」がSPEC 18.1とDESIGN 2.1で食い違う

- **対象**: `docs/SPEC.md` 3.2節・18.1節、`docs/DESIGN.md` 2.1節・15節
- **根拠**: 方針そのものは一致している（Windows版Chrome／Edgeの最新版安定版を対象とし、固定バージョンを埋め込まず受入試験記録に実バージョンを残す）。食い違うのは分類である。

### R8. サービス再起動時の扱いが、「状態を再取得できる」設計方針と読み合わせると曖昧

- **対象**: `docs/DESIGN.md` 5.3節、9章
- **根拠**: DESIGN 9章は「ブラウザとローカル処理サービス間が切断しても、interaction IDが残っている間は状態を再取得できる設計にする」と書き、DESIGN 5.3は「再起動時は未終了IDのcancelと記録削除を試みる」と書いている。前者はブラウザ↔サービス間の切断（サービスは稼働中）、後者はサービス自体の再起動という別の事象を指しているが、同じ「interaction IDが残っている」という語で説明されているため、再起動後に**再開するのか中止するのか**が読み取りにくい。U6の決定は「中止・削除を試みる」であり、DESIGN 5.3が正しい。
- **影響**: 実装者が再起動後の再開機能を作り込んでしまう、あるいは逆にブラウザ再読込のたびに解析が中止される実装になる可能性がある。後者はSPEC 8.5「中止は利用者の意図した操作」に反する。
- **修正案**: 9章の該当箇条書きを「**ブラウザとローカル処理サービス間**が切断しても、サービスが稼働している限りinteraction IDから状態を再取得でき、ブラウザ再読込後も解析は継続する。**ローカル処理サービス自体が再起動した場合**は、U6の決定に従い未終了interactionのcancelと記録削除を試み、再開はしない」と2文に分ける。

### R9. `response_format` 既定ONが、A違反エラー経路の受入試験を実施困難にする

- **対象**: `docs/DESIGN.md` 8.2節、`docs/SPEC.md` 17.3節
- **根拠**: SPEC 17.3の受入条件に「形式の壊れたJSONが返った場合、一部だけを採用せず、再実行を案内するエラーになる」がある。`response_format` を既定ONにすると、構造崩れの応答を意図的に発生させること自体が難しくなり、この受入項目を実地で確認する手段が限られる。U3が定めた画面外設定の無効化スイッチは、まさにこの用途にも使える。
- **影響**: 受入試験時に「確認手段がない」として当該項目が未検証のまま通過するおそれがある。
- **修正案**: DESIGN 8.2へ「画面外設定による `response_format` の無効化は、代表データでの比較検証に加え、A検証エラー経路の受入確認にも用いる」と1行加える。実装上の追加作業は発生しない。

### 確認事項. 動画終端の受入判定を `ceil(実動画長)` で行うことの明示的な了承

- **内容**: R5のとおり、DESIGN 10.3は許容する最大 `end_time` を `ceil(実動画長)` 秒としている。動画長100.4秒なら101秒までが有効値になる。

- **推奨**: (a)。DESIGN 10.3に受入判定の注記を1行加えるだけで済む。
