## 1. 総評

大枠は承認可能な水準。ただし公式仕様との照合で4件の必須修正があり、それらを反映するまでは設計確定としない方が良い。

SPECを変更せずに具体化する姿勢が全編で一貫しており、`predictionOriginal` の不変性、A/B検証の分離、background execution採用、APIキーのローカルサービス隔離、3GB断定回避と実機ゲート化といった主要判断はいずれも妥当。「確定した範囲」と「実装前ゲート」の切り分け（DESIGN 3章・4章・17章・18章）は、実データ未提供の段階で作れる設計書としてはかなり質が高い。

一方で、公式ドキュメントを読んだうえでの詰めが甘い箇所が3か所ある。(a) Interactionの状態集合が公式の列挙と一致しておらず、pollingループが終了しない経路が残る、(b) 動画の実効上限が「容量」ではなく「再生時間」で決まる点が設計ゲートに反映されていない、(c) `duration_seconds` の画面表示規則がSPEC 9.3/15.4と食い違い、受入条件17.3に不合格になり得る。加えて、SPEC 18.1「設計開始前に解決必須」が未解決のまま設計を確定していることを、逸脱として明示していない。

## 2. 必須修正

### M1. Interactionの状態集合が公式列挙と一致せず、pollingが終了しない経路がある

**根拠**: DESIGN 3.6は「`completed`、`failed`、`cancelled`、`incomplete` のいずれかになるまで追跡する」としている。公式APIリファレンスの列挙は次の8値。

> "in_progress", "requires_action", "completed", "failed", "cancelled", "incomplete", "budget_exceeded", "queued"

DESIGNは `requires_action`（"The interaction requires action/input from the user."）、`queued`、`budget_exceeded` を扱っていない。`incomplete` の定義は "The interaction is completed, but contains incomplete results (e.g. hitting max_tokens)" であり、出力トークン上限が主因。DESIGN 9章の「context超過や出力上限による `incomplete`」という記述のうち、入力context超過はおそらく400系エラーであり `incomplete` ではない。

**影響**:
- `requires_action` に遷移した場合、DESIGNの終了条件に含まれないためポーリングが無限継続する。
- `budget_exceeded` は管理者対応（quota/課金）を要する固有エラーだが、13.1のエラー分類表に対応先がなく、一律「再実行」を案内すると利用者が無限に再実行する。
- `incomplete` の原因を出力上限と正しく認識していないため、DESIGNの案内（再実行）が決定論的に同じ失敗を再生産する。

**推奨修正**:
1. 3.6節に公式8状態の完全な遷移表を置く。`in_progress`/`queued` = 継続、`requires_action` = 本MVPでは利用者入力機構を持たないため即時エラー終了（内部相関IDと状態名を記録し「この結果は利用できません。管理者へ連絡」）、`budget_exceeded` = 「設定」分類の管理者向けエラー、`completed`/`failed`/`cancelled`/`incomplete` = 既定どおり終端。
2. 13.1の表に `budget_exceeded`（設定/費用）と `requires_action`（Gemini処理・非対応状態）の行を追加。
3. `incomplete` の案内文を「結果が途中で打ち切られました。同じ入力での再実行では改善しない可能性が高いため、短い動画で試すか管理者へ連絡してください」に変更し、単純な再実行誘導をやめる。
4. 8.1のシーケンスに `max_output_tokens` を明示設定する手順を追加（R3参照）。

### M2. 動画の実効上限は「容量」ではなく「再生時間」で決まる。3GBゲートが容量のみで定義されている

**根拠**: 公式video-understanding。

> "Models with a 1M context window can process videos up to 1 hour long at default media resolution or 3 hours long at low media resolution."
> "Approximately 300 tokens per second of video at default media resolution, or 100 tokens per second of video at low media resolution."

公式document-processingより「Each document page is equivalent to 258 tokens」。42ページPDF ≈ 10,836 tokensで、PDFはcontextをほとんど消費しない。1,048,576 − 約11,000 − プロンプト ≈ 約1,037,000 tokens ÷ 300 tokens/秒 ≈ 約3,450秒（約57分）が既定解像度での実効上限。

DESIGN 3.3は「実際に使える動画時間はPDF分の入力も含むcontext上限に依存する」と書いているが、実際の支配要因はPDFではなく動画の再生時間であり、約1時間という硬い壁がある。3GBという容量目標と1時間という時間上限は独立（3GB／1時間 ≈ 6.8 Mbpsは高品質1080pとして現実的だが、同じ3GBでも2時間の動画なら3.4 Mbpsで成立し、容量チェックは通過してcontextで必ず失敗する）。

**影響**: 現設計のゲート（7.1「目標上限3GBは実機確認ゲート」）は容量しか見ていないため、約1時間超の動画は、数十分かけてアップロードを完走した後に必ず失敗する経路が残る。DESIGN 9章は `incomplete`／context超過を部分成功にせず全体エラーにするため、利用者は待ち時間と通信量と課金を消費して何も得られない。

**推奨修正**:
1. 3.3節と7.1節に再生時間の事前チェックを追加する。ブラウザで取得した動画長から概算入力トークン（`再生秒数 × 300 + PDFページ数 × 258 + プロンプト分`）を計算し、モデルcontext上限に対する見込みを解析開始前に判定。超過見込みならGemini送信前にエラー、境界域（例: 80%超）なら明示的な警告。
2. 6.1の解析前表示に「推定入力規模」または「この動画は上限に近い」という案内を加える。
3. 4章・17章の未確認事項と受入条件を「3GB（容量）」だけでなく「代表動画の再生時間が既定解像度の実効上限内か」に拡張する。18章のチェックリストにも1行追加。
4. 3.3節の「実際に使える動画時間はPDF分の入力も含むcontext上限に依存する」を、実数（PDF 42p ≈ 約1.1万トークン、動画300 tokens/秒）に基づく記述へ差し替える。

### M3. `duration_seconds` の画面表示規則がSPEC 9.3 / 15.4と不整合

**根拠**: SPEC 9.3の表は `duration_seconds` を「画面表示とreviewedでは自動再計算、直接編集不可」と定めている。SPEC 15.4も「`reviewed.json` および画面表示上の `duration_seconds` は、常に開始・終了時刻から再計算する。`prediction.json` は対象外」と明記。SPEC 17.3の受入条件も同様。

対してDESIGN 10.1は「Geminiの各値は `predictionOriginal` で再計算・修正しない。`duration_seconds` の不一致も値を保持して警告にする」とし、DESIGN 6.3は「AI予測（原本）へ切り替えた場合は全項目を表示専用にする」としている。素直に実装すると、AI予測原本ビューにはGeminiの生値がそのまま表示される。

**影響**: SPECの受入条件17.3に不合格になり得る。B検証（duration一致）は生値と再計算値の両方を必要とするため、どちらを画面の正とするかが未定義なままだと実装者が任意に決めてしまう。

**推奨修正**: DESIGN 6.3 / 10.1に次を明記する。
- 画面上の `duration_seconds` は常に開始・終了時刻から再計算した値を正として表示する（原本ビューを含む）。
- 原本ビューでB違反（duration不一致）がある区間は、AI応答値を併記し警告表示する。
- `prediction.json` にはAI応答値のみを出力し、再計算値は出力しない。

### M4. SPEC 18.1「設計開始前に解決必須」項目が未解決であることを、逸脱として明示していない

**根拠**: SPEC 18.1は、Gemini API疎通確認（利用可能なモデル識別名、動画＋PDF同時投入可否、入力上限、アップロード方式、同期／非同期、代表データでの実測処理時間）、最低対応ブラウザバージョン、代表データ先行確認の3件を「設計開始前に解決必須」としている。本設計は、ユーザー方針（実データ・APIキー未許可）により、これらを公式ドキュメントのみで代替して確定している。

DESIGN 1章は前提を書いているが、これがSPEC 18.1の要求からの逸脱であるとは書かれていない。またDESIGN 15章は最低対応バージョンを設計フェーズで確定しない方針であり、これはSPEC 18.1-2の要件の緩和にあたる（判断自体は妥当だが、暗黙に行うべきではない）。

**影響**: DESIGN 18章の受入条件1行目「SPECの要件を削除・緩和していない」を、厳密には満たしていない状態で承認を求めることになる。

**推奨修正**: DESIGN 2章のSPEC対応表または新設の小節に、SPEC 18.1の3項目 × 現在の状態 × 移送先を明示した表を追加する。

| SPEC 18.1 項目 | 現在の状態 | 扱い |
|---|---|---|
| 利用可能なモデル識別名 | 公式一覧で確認済み／検証メモの表記との同一性は未確認 | 実装前ゲートへ移送 |
| 動画＋PDF同時投入・入力上限・アップロード方式・同期非同期 | 公式ドキュメントで確認済み、実測未実施 | 実装前ゲートへ移送 |
| 代表データでの実測処理時間 | 未実施 | 実装前ゲートへ移送 |
| 最低対応ブラウザバージョン | 固定せず「受入試験日の最新安定版」へ変更 | SPEC要件の緩和。ユーザー承認が必要 |
| 代表動画の長さ・コーデック・容量、PDF構成 | 未提供 | 実装前ゲートへ移送 |

そのうえで、「本設計の承認は、SPEC 18.1の解決時期を設計開始前から実装着手前へ移すことの承認を含む」旨を1文で明記する。

## 3. 推奨修正

### R1. B検証「動画範囲内」の実行主体と、終端時刻の丸め規則が未定義
ローカル処理サービスは動画をデコードしないため再生時間を知らない。動画長はブラウザの `loadedmetadata` からしか得られない。DESIGN 7.1は動画時間を小数保持、区間境界を整数秒にするとしているが、動画長が100.4秒のとき `end_time` の上限が100秒か101秒かが未定義。
→ 推奨: (a) B検証のうち「動画範囲内」だけはブラウザ側で実施する、または解析要求時に動画長をサービスへ渡す。(b) 10.3に「許容される最大 `end_time` は `ceil(動画長)` 秒」のように丸め規則を1行で定義。

### R2. 応答パースの許容範囲が未定義。A違反=全損のため、表記ゆれが全損に直結する
検証済みプロンプトは「余計な挨拶や解説テキストは一切出力しない」と指示しているが、コードフェンス付きで返る可能性がある。`HH:MM:SS` の1桁表記や前後空白の扱いも未定義。
→ 推奨: 8.3または10.2に、(a) コードフェンス・前後空白の除去は許容、(b) 正規表現を厳密適用しゼロ埋め補正は行うか否かを明記、(c) `duration_seconds` が文字列で返った場合は型A違反として全体不採用、を明記。(b)はユーザー判断U5に連動。

### R3. プロンプト以外でも結果を左右するAPI設定（`max_output_tokens`・`media_resolution`・thinking設定）が未記載
`max_output_tokens` は `incomplete` の直接原因。1時間動画で区間が多数、各区間が日本語の詳細説明を持つと出力は数万トークン規模になり得る。`media_resolution` も既定採用だが8章のAPI設定として明示されていない。
→ 推奨: 8.2に「APIパラメータ（非プロンプト）一覧」を新設し、`model`／`response_format`／`max_output_tokens`／`media_resolution`／thinking関連設定を列挙し、すべて16.4のログ記録対象に含める。

### R4. pollingのリトライ方針が通常リトライ（最大4回）と混在している
最大4回がジョブ単位なのかリクエスト単位なのかが読み取れない。約300秒＝約60回のポーリング中に一時的な通信断が5回起きただけでジョブ全体を失敗させるのは、background executionを選んだ意義を損なう。
→ 推奨: 3.7に「ポーリングのリトライは解析全体のリトライ回数に算入しない。連続失敗が一定時間（例: 2分）継続した場合にのみ、interaction IDを保持したまま利用者へ通信不安定を通知し、待機継続か中止かを選ばせる」を追記。

### R5. 生応答を一切保持しない方針では、A違反の原因調査が不可能
→ 推奨: 画面外設定（例: `GEMINI_DEBUG_DUMP=1`、既定OFF）でのみ、生応答テキストを一時領域へ保存し、次回起動時の清掃対象に含める。APIキーは含めない。既定OFF・非機密限定・利用者向け画面には出さないことを条件として8.3へ追記。

### R6. localhost構成の保護と、GB単位の二重書き込み
(a) Hostヘッダ検証（DNS rebinding対策）と起動ごとのランダムトークンがない。
(b) 一時保存後にFiles APIへ送る構成のため、ディスク書き込みと転送が二重になる。
→ 推奨: (a)はHostヘッダ検証と起動時トークンを14章へ追加。(b)は現行方式を既定として維持しつつ、理由（再開処理の単純さを優先）を7.3へ1文で残す。

### R7. 「ダウンロード成功」を観測できない
ブラウザのダウンロード（Blob + `a[download]`）は保存完了もキャンセルもJavaScriptへ通知しない。
→ 推奨: 12.2に「ここでいう成功とは、JSON生成と検証が完了しダウンロードを開始できたことを指す。保存先での完了はブラウザが通知しないため保証しない」と定義を明記。

### R8. 3GB確認ゲートが、現有データでは実行できない可能性
SPEC 7.3は「検証動画は2GB以下の見込み」であり、3GBの代表データが存在しない可能性が高い。
→ 推奨: 17.1を「(i) アップロード上限確認: 合成した約3GBのMP4でアップロードのみを試行、(ii) 解析確認: 代表データ（2GB以下）で全工程を実測」の2段に分離。

### R9. SPECの細目でDESIGNが触れていない項目
- 区間追加時の開始時刻初期値＝動画の現在時刻（SPEC 11.2）
- 区間削除前の確認表示（SPEC 11.3）
- 区間の色分け（SPEC 10.3）
- 応答に9項目以外のキーが含まれた場合の扱い（A違反にせず出力時に破棄、と明記）
- 再実行成功で結果を差し替えた際のUndo／Redo履歴の破棄
- DESIGN 16.2「完全成功後にだけ入れ替える」の定義（B警告付き成功は入れ替え対象に含む＝A検証合格が条件、と明確化）
→ 推奨: 10.4・11章・13.3へ1行ずつ追加。

### R10. `prediction.json` の出力順序
`predictionOriginal` を開始時刻昇順に一度並べ替えてから不変化するため、`prediction.json` の要素順がGemini応答と異なり得ることを12.2に明記する。

## 4. 受入可能な設計判断（指摘なし、または軽微な追記のみ）

- background executionの採用（3.6）
- `response_format` の併用（8.2）。ただし過去検証との条件差はU3として判断を仰ぐ
- `predictionOriginal` 不変 ＋ 深い複製の編集（10.1）
- A違反=全体不採用、部分救済なし（10.2・13.1）
- B違反=警告付きで編集継続、`reviewed.json` 出力時は全違反禁止（10.3・12.2）
- 半開区間 `[start, end)` と境界時刻の帰属（10.3・11.2）
- タイムライン拡大機能を必須にしない判断（11.3）
- APIキーの扱い（14章）
- Gemini上の一時ファイル削除方針（3.5・9章・16.3）
- 圧縮・分割（選択肢B・C）をMVPで独断採用しない判断（3.3・17.1）
- PDFの1,000ページ・50MB上限を理由とする拒否（3.4・7.2）
- 段階表示7段階と進捗率非表示（6.2）
- モデル選定（3.1）は条件付き受入。「比較可能性」を根拠にすることの説得力は設計書が想定するより弱い（検証環境がAI Studio Agent Platformであり、API直叩きとは条件が異なる可能性）→ U4として判断を仰ぐ

## 5. ユーザー判断が必要な未決事項

- **U1. 3GB目標の扱い**: 実機確認で3GBを試す（R8の2段階方式を推奨）／確認前にSPECを2GBへ改訂／「MVP保証範囲＝代表データ実測範囲、3GBは未保証の目標値」と定義し直す。推奨は「実機確認＋定義し直す」の併用。
- **U2. 実データ・APIキーによる検証の許可時期と費用上限**: 許可時期に加え、費用の上限も同時に決めるべき。想定実行回数×概算入力トークンを提示し、AI Studioの課金表示で上限を設定してから開始することを推奨。
- **U3. `response_format`（JSON Schema）併用の可否**: 併用する／併用しない／設定で切替可能にし許可された検証時に実測して決める。推奨は最後の選択肢。
- **U4. Preview継続か、初期採用をStableへ変更するか**: DESIGNどおりPreview継続／Stableを初期採用／許可された検証で3候補を同一データで実測してから確定。推奨は最後の選択肢。
- **U5. A検証の厳密性（表記ゆれの正規化を認めるか）**: 厳密適用を既定とし、`response_format` 併用によって発生確率を下げることを推奨（U3と連動）。
