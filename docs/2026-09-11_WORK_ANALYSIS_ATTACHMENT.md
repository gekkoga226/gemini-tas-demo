# 作業みえる：一人称作業動画分析アプリ 仕様書

作成日：2026-09-11／版：0.1
対象：初期ローカル検証からCloud Runでの共有利用へ移行するアプリ
根拠：`gcp_gemini_tas_zero_few_shot_proposal.md` 全16章、同資料のHTML版、および今回の実行環境の指定。

## 1. 目的と今回の成果物

80〜120分の一人称動画から、実際の作業、標準書との差、工程ごとの時間を理解し、現場の担当者が動画を見ながら結果を修正できるようにする。

本仕様書では、今回作る「操作できるモック」と、その後に実装する「Geminiによる実分析」を明確に区別する。モックの数値から対象動画の精度や作業者の能力を判断しない。

| 段階 | 実行場所 | 動画分析 | 保存・利用 |
| --- | --- | --- | --- |
| 今回のモック | ローカルブラウザ。HTMLを直接開く、または同梱サーバーで配信 | 操作用サンプル表示、共通形式の結果JSON読み込み。Gemini未接続 | 動画はブラウザ内、修正はメモリ内。JSON・CSVで持ち出す |
| 初期実分析PoC | ローカルPCのWeb画面＋Python API／ワーカー | GCPのGeminiへAPIで依頼 | ローカルのファイル・SQLite。必要な動画をGCPへ転送 |
| 最終共有版 | Cloud Runサービス＋Cloud Run Jobs | GCPのGemini。長時間処理はJobsが担当 | Cloud Storageと共有データベース。BigQueryは分析用に追加 |

ローカルPoCでもGemini推論はGoogle側で実行される。今回のモックは通信を行わず、動画内容を自動解析しない。Cloud Runへのデプロイは今回の実施範囲に含めない。

## 2. 利用者と画面設計

主な利用者は、動画から気になる作業を確認する現場担当者と、標準や時間を比較する生産技術担当者。専門用語に詳しくなくても操作できる画面にする。

- 主操作は「動画を選ぶ」「作業を選ぶ」「動画で確認」「修正して確認済みにする」。
- Zero-shotは「見本なし」、Few-shotは「見本あり」を併記する。
- 標準への対応を「標準作業」「一部対応」「未記載」「要確認」と日本語で表示する。
- 色に加えて文字を表示する。青緑＝標準作業、黄＝未記載、灰＝要確認。待機・探索などの活動は別欄にする。
- 主要文字16px以上、補助ラベル14px以上を基本にする。ボタンはタッチ操作できる大きさにする。
- 左右2列は動画と区間一覧に使い、狭い画面では縦に並べる。表の横スクロール以外は画面からはみ出させない。
- 読み込み中、未読込、読込失敗、該当結果なし、サンプル／実結果、未保存の修正をそれぞれ表示する。
- キーボード操作、フォーカス表示、フォームラベル、ダイアログの閉じる操作を用意する。

| --- | --- | --- |

| 標準との比較 | 標準書の工程ごとの対応、未観察、未記載一覧、方式比較 | 実装 |

全体のモード切替は両方式のデータを別々に保持し、画面間で同じ選択を使う。片方しか結果がない場合は、未実行側を空状態として表示する。

## 4. モックの操作フロー

1. 初期画面に120分の架空サンプルを表示し、動画再生位置・区間・集計の関係を体験できる。
2. 利用者が対象動画を選ぶ。ファイルをブラウザの動画プレイヤーで開き、再生時間を取得する。
3. 動画を変更したら直前の結果を解除する。「この動画は未分析」を表示する。
4. 「操作用サンプルを表示」を押すと、その動画長に合う架空の区間とZero-shot／Few-shot結果を作る。画面上・出力ファイル上ともサンプルと表示する。
5. 実際の分析結果がある場合は「結果JSONを読込」を押す。動画情報・形式・区間を検証して採用する。
6. 区間を選ぶと動画が開始位置へ移動する。再生中は現在区間の表示を更新する。
7. 2方式を切り替え、標準対応・要確認・時間内訳の違いを見る。
8. 標準ID・対応状態・確認状態を修正する。境界調整は前後区間との連続性を維持して実施する。
9. 結果をJSON、区間表をCSVへ出力する。再読込で修正を再現する。

サンプルの生成は動画内容を使わない。動画を変えた時に以前の結果を流用しない。サンプルのFew-shotの数値が良くても、実際のFew-shot精度を意味しない。

## 5. 入力要件

### 5.1 対象動画

- ブラウザで再生できるMP4・WebM等。拡張子だけで対応可否を判断せず、メタデータと再生エラーを確認する。
- 目標は80〜120分。短い動画でも操作検証できる。120分超は想定外の通知を出し、モックでは読み込みを許容する。
- モックでは一度に1本。大容量動画をbase64化せず、Object URLで再生する。
- 動画入れ替え時と終了時にObject URLを解放する。
- 数値で有限かつ正の再生時間を確認する。破損・未対応形式は理由を示す。

### 5.2 標準書と見本（実分析段階）

- 作業標準書は原文、版、ページ、図の関係を保持する。構造化した標準カードを人が確認する。
- Few-shotは標準動画1サイクルと正解付き区間データを登録する。正解未確認のAI候補を見本へ昇格しない。
- 作業名・対象・工具・場所・開始終了条件ごとの見本を抽出する。未収録クラスは見本なしと記録する。
- 標準動画が標準書の全工程を網羅するとは仮定しない。標準時間と見本動画の実測時間を分ける。

### 5.3 結果JSON（今回実装）

`schema_version = "1.0"`、`video`、`standard_cards`、`modes`を必須とする。サンプルと実結果は`data_source`で区別する。元資料の1区間JSONは部分例なので、そのままでは本アプリの一式ファイルではない。見本ファイルを同梱する。

- `video`：`name`、`duration_sec`、`size_bytes`。結果だけの閲覧では動画未選択を許容する。
- `modes.zero / modes.few`：各モードの`segments`配列。少なくとも一方式が必要。
- `standard_cards`：`id`、`name`、`duration_sec`。標準時間未設定はnull。
- `segment`：`id`、`start_sec`、`end_sec`、`action`、`activity`、`object`、`tool`、`location`、`before`、`after`、`evidence`、`standard_id`、`match_status`、`method_status`、`order_status`、`review_status`、`note`。
- 主タイムラインは先頭0秒から動画末尾まで連続・重複なし。IDはモード内で一意。全値の型を検証する。
- 区間が重なる・抜ける・逆転する・動画範囲を超える場合は拒否し、既存データを維持する。
- 未定義標準IDを拒否する。標準IDが必要な「標準作業／一部対応」と、IDなしの「未記載／要確認」を整合させる。
- 選択済み動画と結果の動画名・容量（記録がある場合）・時間が一致するか確認する。時間許容差は2秒を初期値とし、軽微な差では末尾のみ実動画長へ合わせる。これは本人性の証明ではなく取り違え防止。
- 実分析版は動画ハッシュと版で厳密に結合する。結果JSON内の文字列はHTMLとして実行しない。

## 6. Step1：実際の行動を記録する仕様

標準の手順一覧・順序・標準時間は渡さない。部品名、場所名、撮影条件、分割規則は渡せる。Zero-shot／Few-shotの初期比較では同じ観察結果を利用する。

1. 180秒の本体＋前後15秒のチャンクを作る。元動画時間へ戻すオフセットを保存する。
2. 初期2fpsで全時間帯を観察し、手・物・場所・状態変化から境界候補を作る。
3. 境界前後5〜10秒を5〜10fpsで再確認する。不明区間には前後30〜60秒も付ける。
4. 動作イベントL0から、計時する要素作業L1をまとめる。標準の工程数には合わせない。
5. 重複部分を、時刻・対象・状態で統合する。探索・待機・画面外を消さない。
6. 観察事実、推定した意味、可視性、境界の不確実性、証拠時刻を保存する。
7. 実行順にAs-is作業標準書案を生成する。正式な安全手順・最善手順の承認とは別に扱う。

初期値は原提案の検証条件であり、最適値・精度保証ではない。Agenticの再確認はAPIの提供条件を満たすモデルだけで使用し、全区間走査を省略する根拠にしない。

## 7. Step2：標準比較の仕様

| 方式 | 照合入力 | 出力 |
| --- | --- | --- |
| Zero-shot | 対象区間の動画・証拠パック＋候補標準カード | 対応標準ID、未記載、相違、判定不能、根拠 |
| Few-shot | 上記＋検索した正解付き見本 | 同じ出力形式。見本のID・未収録も保持 |

対象・操作・前後状態・工具・場所で候補を検索し、初期3〜5候補を比較する。候補に正解がない可能性を考慮し、未記載の確定前に検索を拡大する。

標準への対応、方法への適合、順序、初回／再開／繰り返し、確認状態を別軸で保持する。A→探索→C→Bの実行列を、標準A→B→Cへ書き換えない。必須の先行条件が明記された場合だけ順序逸脱候補とする。

標準1工程に複数観察区間を対応づけることを許容する。複数標準が混ざる1区間は再分割するか未配賦で保留し、全時間を各工程へ重複加算しない。今回のモックは1区間1標準IDまでを扱い、多対多の実装は次段階。

## 8. 修正と時間の整合

- 標準ID・対応状態・確認状態・メモをモード別に修正する。
- 境界編集では選択区間の開始変更を前区間の終了へ、終了変更を次区間の開始へ同時反映する。隣接区間を潰す変更や動画外の変更を拒否する。
- 初期・最終の境界は0秒／動画長で固定する。
- 境界が変わった区間と隣接区間は確認状態を未確認へ戻す。修正した対応・観察の確認は動画を見て行う。
- 元の観察とレビュー内容を区別し、実分析版は変更履歴、理由、変更者、前後版を保存する。モックは変更履歴をJSONに保持する。
- モックの境界修正はモード別に保持する。実分析版ではStep1の原版を保持し、そこから派生した分析版として扱う。
- 分割・結合・多人数同時トラックは本仕様に含めるが、今回のモックでは境界調整までを実装する。

## 9. 分析画面の計算規則

| 表示 | 計算・表示規則 |
| --- | --- |
| 総時間 | 動画全体の長さ。モックは全体を1サイクルとして扱う |
| 未記載時間 | `match_status = unmatched`の区間長合計 |
| 要確認 | `review_status != verified`の件数。対応不明と同じ意味ではない |
| 標準工程の時間 | 同じ標準IDの主区間長を合計。中断・別活動は独立して残す |
| 山積み | 一人分の工程別時間を積み上げ、未記載・判定不能・一部対応も残す。基準TT80分線を表示 |
| ガント | 元動画秒を横軸にして実行順を表示。クリックで元区間へ移動 |
| バレット | 標準カード時間を目標線、実測を棒で表示。標準時間なしは比率を出さない |
| 方式比較 | 同じ動画のZero-shotとFew-shotで件数・分類時間を比較。精度の比較とは呼ばない |
| 実施手順書 | Step1観察の実行順。作業、開始終了状態、工具・場所、時間、証拠を含む |

TT、標準カードの時間、見本実測を別々に保持する。1サイクルのみから習熟の統計やボトルネックを確定しない。ライン全体の山積みには他の作業者・設備の同期データが必要。

## 10. システム構成とCloud Runへの移行

### ローカルPoC

画面はブラウザ、APIはローカルFastAPI、長時間処理は別Pythonワーカープロセス、動画分割はFFmpeg、Gemini呼出しはGCP接続のアダプターが担当する。結果は本仕様のJSONへ変換して画面に渡す。ローカルSQLiteにはジョブ・レビュー・版を記録し、大きな動画はファイルとして保持する。

今回のモック画面はビルド不要のHTML/CSS/JavaScript。UIと計算処理を分けたため、後からAPI呼び出しへ接続できる。React採用は現行リポジトリへ統合する時に判断し、今回の操作検証の前提にしない。

### 共有利用版

| 要素 | Cloud Run段階 |
| --- | --- |
| UI・API | Cloud Runサービス。同じオリジンで配信し、社内利用者を認証 |
| 原本と派生物 | Cloud Storage。大容量動画は再開可能な直接アップロード経路を使用 |
| 長時間分析 | Cloud Run Jobs。サービスへの1リクエスト内で80〜120分動画の処理完了を待たない |
| ジョブ・レビュー | 共有のトランザクション可能なDB（例：Cloud SQL）。SQLiteやコンテナ内ファイルを共有保存に使わない |
| 分析集計 | BigQueryへ確定結果を連携。初期はAPI側で集計可能 |
| 実行管理 | APIからジョブを起動。依存段階が複雑になった時にWorkflowsを追加 |

Cloud Runサービスは`PORT`で指定されたポートで全インターフェースを待ち受ける。コンテナ内ファイルは永続保存先にしない。Jobsはタスク単位で再試行とタイムアウトを設定する。[Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract)、[Cloud Run Jobs](https://docs.cloud.google.com/run/docs/create-jobs)

同梱Dockerfileは今回の静的モック配信用。実Geminiワーカー、DB、認証、動画アップロードを実装した本番構成とは別の成果物である。

## 11. 実分析API契約（次段階）

| API | 役割 |
| --- | --- |
| `POST /api/videos` | 動画の登録。ローカルは受信ファイル、クラウドはアップロード先を返す |
| `POST /api/references` | 標準動画・確認済み正解・標準書版を登録 |
| `POST /api/analyses` | video_id、mode、reference_id、設定版を受けてjob_idを即時返却 |
| `GET /api/analyses/{job_id}` | 状態、処理済みチャンク数、失敗した箇所、費用の取得 |
| `POST /api/analyses/{job_id}/cancel` | 未着手処理の停止と実行中チャンクの安全な中断 |
| `GET /api/results/{result_id}` | 検証済みの共通JSON形式で返却 |
| `PATCH /api/results/{result_id}/segments/{id}` | 期待する版と修正内容を送り、競合時は409 |
| `GET /api/results/{result_id}/export` | JSON・CSV出力。修正状況とサンプル種別を含める |

ジョブ状態は`queued → preprocessing → step1 → step2 → validating → needs_review/completed`。途中から`failed/cancelled`へ遷移できる。再実行キーは動画版・設定版・チャンク・段階から決める。API一時失敗のみ再試行し、同じ結果を二重登録しない。

Gemini認証情報はブラウザへ置かない。ローカルでは利用者の適切なGCP認証、Cloud Runではサービスアカウントを使う。モデルID・API版・SDK版を設定として固定し、原提案のモデル名を無条件に最新版として扱わない。

## 12. 非機能要件

- 動画やJSONの読み込みで画面全体を固めない。区間一覧は原則最大5,000区間を初期上限とし、超える結果を拒否する。
- 動画の全バイトをJavaScript配列へ展開しない。結果JSONは10MB以下をモック上限とする。
- 未保存の変更がある場合は動画切替・結果入替時に確認する。ページ再読み込み時はブラウザの標準確認を用いる。
- CSV出力はセル先頭の`= + - @`などを安全に扱い、表計算ソフトで式として実行されないようにする。
- モックは動画・結果を外部へ送信しない。継続保存はJSONダウンロードで利用者が行う。
- 本番は動画・結果へのアクセスを利用者権限で制御し、保存期間と監査履歴を社内運用に合わせて定める。
- 対象動画から見えない意図、必要性、品質結果をAIの断定として表示しない。

## 13. 検証と受入条件

### 今回のモックの受入

| ID | 条件 |
| --- | --- |
| M01 | 動画を選択してローカル再生でき、長さとファイル名を表示する |
| M02 | 動画変更で古い結果を解除し、未分析を明示する |
| M03 | サンプル生成後に2方式の結果を切り替え、区間・比較・時間分析を表示できる |
| M04 | 区間選択・時間軸操作で再生時刻へ移動できる |
| M05 | 対応・確認状態・境界の変更が集計へ反映される。違法な区間は拒否する |
| M06 | JSON保存→再読込で結果を再現し、無効データの読込で既存結果を壊さない |
| M07 | JSON・CSVにサンプル／読込結果の種別と方式を残す |
| M08 | 山積み・ガント・バレットが同じ区間データから計算される |
| M09 | 標準外と判定不能が残り、標準順へ強制的に並べ替えられない |
| M10 | 外部ライブラリやGemini接続なしでモックを起動できる |

今回の自動確認は構文・データ計算・JSON検証・入出力契約を中心にする。ブラウザ上の実操作確認は別途実施状況を納品メモへ明記する。

### Gemini実分析の受入

Step1単体で境界F1、区間IoU、短い動作の見逃しを測定する。Step2単体は人の正解区間でMacro-F1、標準外のRecall／Precision、検索Recall@Kを測る。通しはF1@10/25/50、Edit、MoF、工程時間MAE／WAPE、人の修正時間を測る。

見本・調整・最終評価の動画を分け、80分前後と120分近くの全サイクルを含める。採用目標は原提案の仮値を起点とし、現場が許容する誤差で決める。モックの方式差を精度評価へ流用しない。
