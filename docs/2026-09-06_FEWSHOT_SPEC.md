## 1. 背景と目的

### 1.1 現状

本リポジトリは製造業の TAS（Temporal Action Segmentation＝作業動画の工程区間分割）デモである。現時点で以下の状態にある。

- アプリは**動画も PDF も Gemini に送っていない**。実 API モードは固定テキストを送る疎通確認のみ
- 画面に「動画・PDF は Gemini へ送信しません」と明記している
- `reference/validated_prompt.md` は Google AI Studio で手動実行された検証済みプロンプトで、**アプリ経由で動いた実績はない**
- 精度の実測値は 50〜80% のばらつき（`reference/gemini_validation_notes.md`、Pro での測定）
- 既存記録では `npm test` は18/18 pass（今回の文書改訂で再実行した結果ではない）

### 1.2 Few-shot に期待する役割

**第一目的はラベル語彙・粒度の固定である。時刻の数秒のズレは許容する。**

理由は、本機能の先にある用途①②が、いずれも**複数の動画にまたがって同じ要素作業を同じラベルで集計する**ことを成立条件とするためである。動画Aで「ねじを仮締めする（job_no:120）」と出た作業が動画Bでも同じ `job_no`・同じ `job_title` で出なければ、山積みも差分抽出も成立しない。

開始・終了が数秒ずれても集計は可能だが、**ラベルの表記ゆれや粒度のブレは集計そのものを不能にする**。

> **未検証の中心リスク**: Stage1 の文章化で、視覚的に似た別工程を区別する情報が失われ、動画を見ない Stage2 が語彙内の別工程へ静かに誤ラベルを付ける可能性がある。項目化した観察記録（案1）、Stage1への語彙補助（案2）、Stage2への映像根拠追加（案3）を切り替えて検証する。Check 7で文章照合、Check 8で固定区間の限界、Check 9で通常運用、Check 10で見逃し、Check 11で映像の追加価値を測る。いずれも未実施であり、安全網だけでリスクが解消したとは扱わない。

### 1.3 想定運用

- 作業動画: 20分程度、30〜60区間
- 入力映像: 一人称視点（ウェアラブルカメラ）

## 3. 用語

| 用語 | 定義 |
|---|---|
| **標準作業動画** | お手本となる作業を撮影した動画。Few-shot の例示元であり、対比表示の上段に表示する |
| **実作業動画** | 分析対象の動画。対比表示の下段に表示する |
| **標準作業セット** | 標準動画・作成専用GT・語彙に対応付けたお手本記述・代表静止画・版と出自を持つ不変の資産（8.2） |
| **正解ラベル（GT）** | 人が作った区間・ラベル。標準GTはセット作成時の境界固定と評価に限定し、原本を通常推論に渡さない。実作業GTは採点専用、Check 7だけ境界を匿名化して使用 |
| **お手本** | セット作成時に検証・確定したラベル付き観察記録。GTファイルや正解工程列そのものとは分けた推論用ビュー |
| **分析方式** | `analysis_strategy`。`text_only` / `vocabulary_guided` / `visual_evidence`。Zero/Fewのモードやagentic/staticとは別軸 |
| **GEAP** | Gemini Enterprise Agent Platform。2026年4月に Vertex AI から改称された Google Cloud の AI 基盤 |
| **agentic モード** | Gemini が動画のどこをどの解像度で見るかを自ら決める処理方式。対比語は static |
| **static モード**（Round 16 で追加） | agentic の対比語。動画全体を既定の解像度・サンプリングレートで一様に処理する従来方式 |
| **Stage 1 / Stage 2** | 第5章で定義する2段階パイプラインの各段 |

## 4. 実行環境

### 4.1 API

| 項目 | 値 | 備考 | 確度（Round 16 で追加） |
|---|---|---|---|
| プラットフォーム | **GEAP（旧 Vertex AI）** | 企業の GCP 環境を使用 | ★確認済み |
| API バージョン | **`v1beta1`（必須）** | `mediaProcessing` フィールドが `v1` の `Part` に存在しないため | ★確認済み（Discovery ドキュメント） |
| エンドポイント | `https://{LOCATION}-aiplatform.googleapis.com/v1beta1/projects/{PROJECT}/locations/{LOCATION}/publishers/google/models/{MODEL}:generateContent` | 改称に伴うホスト名変更の可能性があるため設定で上書き可能にする | 要検証（ホスト名） |
| 処理モード | `Part` 直下に `"mediaProcessing": "AGENTIC"` | Discovery ドキュメントで確認済み | ★確認済み |
| モデル | Flash 系 + agentic を主軸 | **確定は検証ゲート項目6の結果による**（第12章） | 要検証（Pro の agentic 対応。第12.1節） |

> **注意**: 非対応モデルに `AGENTIC` を指定してもエラーにならず、静かに `STATIC` にフォールバックする。応答内の `processing_call` / `processing_result` の有無でしか判別できない。

### 4.2 動画の受け渡し

**Cloud Storage（`gs://` URI）が唯一の実用的手段である。**

| 方法 | 可否 | 制約 |
|---|---|---|
| **Cloud Storage `gs://`** | ✅ **採用** | リクエスト元と同一プロジェクト内、または公開読み取り可能であること |
| Files API | ❌ | **GEAP に存在しない**（Discovery ドキュメントで確認） |
| inline base64 | ❌ | リクエスト総サイズ 20MB 程度が上限。20分動画（200MB〜2GB）は不可 |
| HTTP 公開 URL | ❌ | 動画は 15MB 以下 |
| YouTube URL | ❌ | 業務動画には使用しない |

### 4.3 IAM

**バケットを読むのは呼び出し元ではなく Agent Platform のサービスエージェントである。** これを失念すると HTTP 403 で失敗する。

| 対象 | 必要なロール |
|---|---|
| 呼び出し元のユーザー／サービスアカウント | `roles/aiplatform.user` |
| `service-{PROJECT_NUMBER}@gcp-sa-aiplatform.iam.gserviceaccount.com` | 対象バケットに `roles/storage.objectViewer` |

アップロード・削除を行うサーバーの認証主体には、別途、一時保管先でのオブジェクト作成・取得・削除権限を付ける（設計：専用バケットに `roles/storage.objectUser` を付与する構成を環境担当が確認）。呼び出し元の権限を付けても、サービスエージェントの閲覧権限の代わりにはならない。

### 4.4 制限

| 項目 | 値 |
|---|---|
| 動画長の上限 | 音声あり **約45分** / 音声なし **約1時間** |
| 1リクエストあたりの動画本数 | 本アプリでは**必ず1本以下**。従来記録のAPI最大10本は採用上限に使わない |
| 既定のサンプリング | 1 FPS（`videoMetadata.fps` で変更可能、有効範囲 `(0.0, 24.0]`） |

### 4.5 リージョンとデータ保持

**検証段階ではリージョンを限定しない。本番化時に東京リージョン＋ゼロデータ保持（ZDR）への切り替えを検討する。**

本番化時に必要となる設定を以下に記録する。

- **ZDR はプロジェクト単位で明示的に有効化が必要**。既定では入出力が 24 時間保持される（学習には使用されない）
- **データ所在地を限定するにはリージョナルエンドポイントが必要**。グローバルエンドポイントはデータレジデンシー非対応
- agentic モードが東京リージョンで利用可能かは**未確認**

### 4.7 認証（実行場所別の設計）

| 場所 | 採用する認証 | 更新・失敗時 |
|---|---|---|
| ローカルPCの開発・検証サーバー | 既存プローブと同じ `gcloud auth print-access-token`。ログイン済みgcloudと設定済みプロジェクトを運用前提とする | 各API試行前にサブプロセスで取得。401は再取得して1回だけ再試行。ログインが必要なら `AUTH_REQUIRED` で失敗を保存し、人がログイン後に再試行 |
| Cloud Runに配置する場合 | Cloud Runサービスアカウントの実行環境認証。ローカルのgcloudログイン・利用者トークンは持ち込まない | 認証アダプターで実行環境の短期トークンと期限を取得し、期限前に更新。実環境で疎通を確認してから利用 |

認証は `getAccessToken()` 相当の独立した窓口にする。秘密鍵JWT署名の自前実装を要件にしない。アクセストークンはメモリ内だけに置き、履歴・JSON・ログ・ブラウザへ保存／送信しない。履歴には認証方式と呼び出し主体の識別名だけを保存する。既存プローブの環境変数による固定トークンは短時間の疎通用で、非同期サーバーの長時間更新方式にはしない。

### 4.8 実行場所とローカル試行

**Cloud Runは必須前提ではない。開発・検証はローカルPCのサーバーからGEAPを呼ぶ。** ただし20分動画はPCから直接GEAPへ渡せず、一時的にCloud Storageへアップロードして `gs://` URIを渡す。どちらの実行場所でも第4.3節のサービスエージェントへの閲覧権限が必要である。

本番・共有環境の配置先は**今回未確定**。Cloud Run等を選択できるが、PCの永続フォルダに相当する保存先、ジョブ実行主体、再起動後の回復、削除再試行を用意してから移す。Cloud Runの一時ディスクやHTTP応答後の処理継続を、永続ジョブの代わりにしてはならない。

ローカルで必要なのは、Node.js 20以上、gcloud、FFmpeg/ffprobe（音声除去・代表画像抽出）、作業者の同意、プロジェクト・バケット・権限、動画の常設保存先と履歴保存先である。起動時に存在・書込可否・認証取得を確認し、失敗理由を画面へ表示する。ブラウザを閉じてもサーバープロセスが動いていれば継続する。PCの休止・終了では停止し、次回起動時に第8.8節の回復を行う。動画一時保存・削除再試行・実行履歴は配置先にかかわらず必須とする。

## 5. 推論パイプライン

### 5.1 全体構成

**2段階とする。**

以下はすべて正式な分析方式とし、同じ動画・標準作業セット・モデル・実行条件で切り替える。初期選択は `text_only`（精度優位が確認済みという意味ではない）。方式は精度比較のための実験軸であり、自動で他方式へ切り替えない。

| `analysis_strategy` | 画面名称 | Stage1 | Stage2 |
|---|---|---|---|
| `text_only` | 案1：項目化した文章照合 | 語彙なし。区間と項目化観察記録 | 観察記録・語彙・識別条件・標準のお手本記述のみ |
| `vocabulary_guided` | 案2：語彙補助の文章照合 | 語彙と識別条件あり。区間と同じ観察記録。最終ラベルは禁止 | 案1と同じ文章照合 |
| `visual_evidence` | 案3：映像根拠併用 | **案1と同一の実Stage1出力** | 案1の入力＋実作業動画1本＋標準工程の代表静止画列。標準フル動画は禁止 |

下図は共通の骨格を表す。案2のみStage1へ語彙・識別条件を足し、案3のみStage2へ実動画・標準画像を足す。通常推論へGT原本を足す経路は作らない。

```
【事前に1回だけ／標準作業セットごと】
  正解ラベル JSON（既存）の区間境界 ──▶ Stage 1（境界固定モード） ──▶ 視覚記述
  標準作業動画 ───────────────────▶      │
                                          ▼
                                 【お手本】として保存
                        （区間・ラベルは既存GT、視覚記述のみ新規生成）

【毎回／実作業動画ごと】
  実作業動画 ──▶ Stage 1（境界発見モード） ──▶ 区間 + 視覚記述 ──┐
                                                  │
  ラベル語彙（作業標準書 PDF から抽出）───────┤
                                                  ▼
                                              Stage 2 ──▶ 区間 + ラベル + 確信度
                                                  ▲
                          【お手本】───────────┘（Few-shot モードのみ）
```

**標準作業動画側の区間境界について**: 標準作業セットには既存の正解ラベル JSON があり、区間境界とラベルはすでに確定している。したがって標準作業動画に対する Stage 1 は、**区間を新たに発見する処理ではなく、GT の区間境界を入力として与え、その区間ごとに視覚記述を生成する処理**とする（境界固定モード）。実作業動画に対する Stage 1 は区間境界を自力で発見する（境界発見モード）。

**この使い分けの理由**: 標準作業動画のStage 1出力とGTの区間が独立に生成されると、両者の対応付け（境界のズレ・区間数の不一致）という新たな曖昧さが生じる。境界を固定して視覚記述だけを生成させれば、この曖昧さは原理的に発生しない。第5.5節の「同一のStage1プロンプトを通す」は、**視覚記述の書き方・文体が同一であること**を指す。境界情報を入力として与えるか否かは、この同一性を損なわない付随的な違いとして扱う。

標準の作成処理はGTから `{segment_id,start_s,end_s}` だけをStage1へ渡す。IDは工程名を含まない連番である。出力を作成処理内でGT工程に対応付け、人が確認してお手本として公開する。通常のStage2へ渡すのは、そのお手本の観察記録と語彙ラベルであり、GTの時系列・GT原本・評価の注記ではない（8.2）。案2でもGT区間ごとの正解ラベルはStage1に渡さない。

### 5.2 Stage 1（区間分割）

| 項目 | 内容 |
|---|---|
| 入力 | 動画1本（`gs://` URI） |
| 出力 | 境界発見：区間とObservation。境界固定：指定IDとObservationのみ（以下） |
| **ラベル語彙** | 案1・3では渡さない。案2だけ語彙・識別条件を渡す |
| 処理モード | agenticが初期設定。staticとの測定は別条件として保存 |

**案1・3で語彙を渡さない理由**: 語彙に引きずられて区間が歪むリスクを避けるため。案2では区別すべき差を観察する利点を検証するが、語彙の並びは手順命令にしない。工程の抜け・反復・順序変更を埋め合わせず、観察した区間を出す。汎用性はプロンプト本文をドメイン非依存に保つことで担保し、案2のキャッシュは業務語彙に依存する。

> **既知の限界**: ラベル語彙を渡さないことで、視覚的に似た別工程（例: 見た目が近い2種類のねじ締め作業）に対して Stage 1 が似た視覚記述文しか書けない可能性がある。この場合、動画を持たない Stage 2（第5.3節）はテキストだけでは両者を区別できない。緩和策は第9.3節。

#### 5.2.1 共通Observation（必須契約、`observation.v1`）

以下は標準側・実作業側・全方式で**同じ意味の項目**を使う。自由記述の1欄への代用は禁止。不明を推測で埋めず、工具の型番・内部状態・停止原因等を外見から断定しない。

| キー | 意味／型 |
|---|---|
| `objects_parts` | 対象物・部品。名称不明なら見えた形・色まで |
| `work_location_fixture` | 作業位置・治具・組付け箇所。左右は作業者視点と明記 |
| `tools_held` | 工具・手で持つもの |
| `operation` | 操作内容。両手／片手の動き、持替えも含む |
| `state_before` | 区間開始側で観察できる状態 |
| `state_after` | 区間終了側で観察できる状態 |
| `audio_cues` | 音の手がかり。音声なしなら `not_applicable` |
| `unobserved_occlusions` | 観察できなかった事項・遮蔽の配列。各要素 `{field,reason,evidence_ids}`。なしなら `[]` |
| `insufficient_discriminative_features` | 識別に有効な特徴不足の自己申告、boolean。標準の境界固定でも必須 |
| `insufficiency_reasons` | 不足理由の文字列配列。自己申告trueなら1件以上、falseなら `[]` |
| `evidence` | 観察根拠の配列。各要素 `{evidence_id,source,start_s,end_s,description}` |

先頭7項目はすべて `{status,value,evidence_ids}` の同形オブジェクト。`status` は `observed / unknown / not_applicable`、`value` は observed時に非空文字列、それ以外は `null`、`evidence_ids` は観察根拠IDの配列。observedには根拠1件以上が必要。unknownとnot_applicableの理由は `unobserved_occlusions` に書く。観察不足を理由に語彙で補完しない。自己申告falseは識別可能性の保証ではない。

`evidence.source` は `video / audio`。時刻はその動画の先頭を0とした秒で、指定区間内の `start_s <= end_s`（瞬間の根拠は同値可）。音声なしでaudio根拠は不正。モデル内部の思考過程は求めず、「何秒に何が見えたか／聞こえたか」を短く記録する。

#### 5.2.2 境界を持つ外側の構造は分離する

- 発見応答：`{schema_version:"stage1.discover.v1",segments:[{segment_id,start_s,end_s,boundary_evidence,observation}]}`。`boundary_evidence` は `{start_reason,end_reason}` の文字列。区間は半開区間 `[start_s,end_s)`、秒数値（小数可）、先頭0、末尾は入力動画長、正の長さ、連番ID、時系列順。隙間・重複・範囲外は禁止。非作業部分も区間として記述する。
- 固定応答：`{schema_version:"stage1.fixed.v1",observations:[{segment_id,observation}]}`。入力したすべてのIDを一度ずつ返す。**区間時刻・境界根拠・ラベルは返さない**。根拠の観察時刻は返せるが境界変更には使わない。
- いずれもモデル出力の `job_no / job_title / final_label` 等の最終ラベルフィールドは禁止。案2の記述でもラベルIDを回答欄の代用にせず、見えた特徴を書く。
- 不正な応答は自動でソート・区間結合・穴埋めせず、原文とエラーを保存し `INVALID_STAGE1` とする。警告を表示して確認できるが、成功キャッシュ・通常Stage2へ進めない。固定応答をGT区間へ結合するのはサーバーの作成／診断処理だけである。

### 5.3 Stage 2（ラベル付与）

| 項目 | 内容 |
|---|---|
| 入力 | Stage1記録＋語彙・識別条件＋お手本（Few-shot時）。案3のみ実動画と標準代表画像も追加 |
| 出力 | 固定IDごとの最終ラベル、生の確信度、候補、同着、採用根拠（5.3.1） |
| 動画 | 案1・2は渡さない。案3は実動画1本のみ |

**Stage 2 は区間の時刻を変更する権限を持たない。**

> 案1・2の文章照合は未検証であり、案3の映像併用でも改善は未確認である。案3もStage1が二工程を一つに結合した区間は復元できない。Check 7〜11で段階別に判断する。

#### 5.3.1 Stage2応答と保存契約（`stage2.v1`）

モデル応答は `{schema_version:"stage2.v1",labels:[...]}`。labels各要素の必須項目は次の通り。外側に時刻を持たず、入力ID集合との完全一致をサーバーで検証する。

| キー | 型・規則 |
|---|---|
| `segment_id` | Stage1入力IDの文字列。欠落・重複・未知IDは不正 |
| `final_label` | `{job_no,job_title}`。語彙の組に完全一致。判別不能・同着で決められない場合は `その他` |
| `confidence_raw` | モデル自身の確信度、0〜1の有限数値。正解確率として保証しない |
| `candidates` | 最大3件、スコア降順。各要素 `{job_no,job_title,score,reason,evidence_refs}`。1件以上、重複なし、scoreは0〜1。確率和1は要求しない。最終ラベルがその他の場合以外は候補に含める |
| `tie` | boolean。複数の最有力候補を観察根拠で区別できない自己申告 |
| `adoption_reason` | 非空文字列。採用根拠または判別できない理由。順序だけの採用は禁止 |
| `evidence_refs` | 根拠配列。テキスト：`{kind:"observation",segment_id,field,evidence_id}`、お手本：`{kind:"example",example_id,field,evidence_id}`、実動画：`{kind:"actual_video",video_id,start_s,end_s}`、標準画像：`{kind:"standard_image",image_id}` |

参照先が存在し、入力に含まれていることを検証する。案1・2で動画／画像根拠、Zero-shotでお手本／標準画像根拠を返すのは不正。動画根拠は対象区間内に限る。その他以外の採用には実作業の観察に結び付く根拠1件以上を要求し、お手本だけを根拠にしない。`tie:true` は候補2件以上かつ最終ラベルその他とし、違反は不正出力とする。候補や根拠の取り違えもCheck 7・11で目視監査する。

サーバーはモデル応答を保持し、保存版の各labels要素へ次を追加する（モデル値を信用して計算を省かない）：

- `tie_detected = tie || (候補数>=2 && 先頭score−第2score <= tie_margin)`。初期 `tie_margin=0.05`。
- `forced_low_confidence = tie_detected`、`confidence = forced_low_confidence ? min(confidence_raw,forced_confidence_cap) : confidence_raw`。初期capは0.49。語彙内の候補を同着からサーバーが勝手に選び直すことはしない。
- `review_reasons`：`stage1_insufficient / standard_insufficient / forced_low / ordinary_low / fallback / quality_warning` の集合。実Stage1自己申告、お手本根拠に用いた標準記述の自己申告、強制低下、強制でない生の確信度が閾値未満、その他、5.6の警告に対応する。
- `review_required = review_reasons.length > 0`、`auto_accepted = !review_required`。初期 `review_threshold=0.70`。これは画面で確認対象に振り分ける設計既定値で、精度合格ラインではない。設定版 `safety_policy_version` を保存する。capは常に閾値未満とする。

不正な語彙・時刻追加・ID欠落等は `INVALID_STAGE2` とし、自動採用しない。不正出力を黙って語彙へ寄せる／修復することは禁止。生応答と検証エラーを残し、再試行は8.8に従う。

### 5.4 動画は常に1リクエスト1本とする

標準作業動画と実作業動画を**同一リクエストに入れない**。

**理由**: 以下の運用上の利点がある。

1. Google 公式の「最適な結果には1リクエスト1動画」という推奨に沿う
2. 複数動画のタイムスタンプの帰属を区別する公式な方法が存在しないという問題を回避できる
3. 標準作業の処理結果を使い回せるため、毎回20分の動画を送り直さずに済む

> **この決定の位置づけ（Round 16 で修正）**: 「2段階構成では動画2本を同時に入れる場面が存在しない」は、Stage 1 を1本ずつ処理する設計に**した後の結果**であり、この設計を選んだ理由にはならない（循環論法。第15章 R11 参照）。この決定が本来答えるべきだったR5の懸念——「長くて視覚的に類似した工程を、Stage 1 が1本の動画の中だけで正しく切り分けられるか」——は、動画2本の同時投入とは別の問題であり、**Stage 1 単体の精度問題として第10章のサブセット指標で測る**（第10.2.2節・第12章 Check 2 参照）。上記1〜3はいずれも運用上のメリットであり、精度面の反証ではない。

### 5.5 標準作業と実作業は同一の Stage 1 プロンプトを通す

**同じ方式系列・プロンプト版・Observation定義を使う**。案1・3は共通系列、案2はguided系列で標準／実作業を揃える。境界固定／発見は別ファイル・別の外側スキーマを維持する（Round 17）。記述の意味を揃えることは設計上の必要条件であり、照合精度の十分条件ではない。標準側の観察不足も保存し、採用根拠に使う場合は確認対象へ回す。

### 5.6 品質警告

以下を検出して画面に警告として表示する。**自動修正は行わない。**

- 標準書の工程順序に対する逆転
- 標準時間からの大幅な逸脱
- 工程の抜け
- 区間の重複・逆順・隙間
- 語彙にないラベルの出力

警告の初期規則 `quality-policy.v1`：作業ラベルの既知standard_orderが直前の作業ラベルより小さい場合は逆転、同値の反復は逆転としない。standard_duration_sがある区間で標準の0.5倍未満または2倍超なら時間逸脱、standard_order付き作業ラベルが動画内に一度もなければ工程抜け候補。標準書に根拠がなければ判定しない。警告は異常や誤りの断定ではない。逆転は該当2区間、時間は当該区間を確認対象とし、抜け候補は動画全体の警告なので全区間にquality_warning理由を付ける。確認負担への影響をCheck 10で測る。時刻不整合・語彙外は警告として見せると同時に契約違反として成功結果を停止する。

**新規に追加する警告は `public/segments.js` の系譜（DOM非依存の純粋関数）に実装し、テストを書く。** `src/schema.js` の既存 `qualityWarnings` は拡張しない。

> **既知の課題（第14.3節）との関係**: 現状、警告生成ロジックは `public/app.js` と `src/schema.js` に重複して存在し、判定基準が異なる（既知の未対応課題）。この重複の解消自体は本機能のスコープ外だが、**今回追加する警告によってこれ以上重複を増やさない**ため、集約先を `public/segments.js` に一本化する。将来的に `src/schema.js` 側をこちらへ統合する方針とする。

### 5.7 確信度

Stage 2 は各区間に確信度を出力する。**確信度の低い区間を画面で目立たせる。修正は人が行う。**

低確信度区間だけを高フレームレートで再問い合わせする機能は**本機能には含めない**。案3の全区間Stage2映像入力は正式に含める。追加の高FPS再確認が必要かは実測後に判断する。

> **Round 17 で追記**: 第9.3節 制約8による強制的な確信度低下（`forced_low_confidence: true`）は、モデル自身が迷って確信度が下がったのとは別要因である。分布観測はこのフラグが立っている区間を除外して行い、機械的な低下を実際の認識精度の低さと取り違えないようにする。

### 5.8 Zero-shot モードも2段階とする

**Zero-shot と Few-shot の違いは「お手本の有無」だけとする。**

各方式の中で比較する。両方に同一の語彙・識別条件を与え、実作業Stage1の同一実体を共有する。Zero-shotは標準記述・標準画像を送らず、案3でも実動画は送る。Few-shotは対応方式の標準記述を追加し、案3では標準画像も追加する。選択済み標準セットIDはZero-shotにも比較文脈として記録してよいが、APIへお手本を送らず `examples_used=false` とする。

段数が異なると、精度差が「お手本の効果」なのか「2段階化の効果」なのか判別できず、第10章の比較が成立しない。

`reference/validated_prompt.md`（1段階）は**凍結し、文書としての基準点として保全する**。アプリの Zero-shot はこれとは別物になる。

### 5.9 音声

**設定で切り替え可能とする。既定値は音声なし**（設計判断）。音声なしはFFmpegで音声トラックを除去した派生動画をアップロードし、ffprobeで音声トラックが無いことを確認する。「音を無視せよ」という指示だけで代用しない。変換後の動画ハッシュ・長さ・変換ツール版／引数を保存する。映像を再エンコードせず、時刻原点と動画長を保持する。保持できない変換は失敗とする。

比較では標準と実作業の音声条件を揃え、案3のStage2にも同じ派生動画を渡す。音声ありでも会話から個人や作業意図を推測せず、観察できる作業音だけを根拠とする。

- 音声あり: 工具音・金属接触音が境界の手がかりになる。動画長の上限が約45分に下がる
- 音声なし: 上限が約1時間に上がる。作業者の会話が送信されない

## 6. ラベル語彙

### 6.1 構成

ラベル語彙は**2つの層**から成る。

| 層 | 出所 | 内容 |
|---|---|---|
| **正味作業ラベル** | **作業標準書 PDF から抽出** | `job_no` と `job_title`。工程ごとに定義される |
| **非作業ラベル** | **本書で定義（固定）** | 標準書に現れない作業・非作業（第6.3節） |

### 6.2 制約

- **ラベルは語彙に列挙された値と完全一致させる。言い換え・新規創作を禁止する**
- `job_no` を標準作業と実作業の**対応キー**とする
- 判別不能な区間には受け皿ラベル（`その他`）を許可する

### 6.3 非作業ラベル（7種）

サーブリック（動素）分析の**有効／無効の考え方を、要素作業〜単位作業レベルに投影したもの**である。**動素そのものではない。**

> **粒度に関する注記**: サーブリックの動素は 0.1〜1秒オーダーの微細動作を指す。本機能の区間は 20〜40秒であり、JIS Z 8141 の階層では「要素作業の粗い側〜単位作業」に相当する。動素とは約2桁の粒度差がある。動画AIの先行研究・製品は例外なく4〜7クラスへ圧縮しており、18動素すべてを自動認識した事例は確認できていない。

| ラベル | サーブリック由来 | JIS Z 8141 作業分類 | 内容 |
|---|---|---|---|
| `検査・測定` | 検査する | 付随作業 | 品質確認、寸法測定 |
| `運搬・段取り` | 空手移動／運ぶ／つかむ／放す／前置き | 準備段取作業 | 部品・工具の移動、治具セット、後片付け |
| `探索・確認` | 探す／見出す／選ぶ／考える | 職場余裕 | 探す、選ぶ、図面を見る、迷う |
| `手待ち（外因）` | 避け得ぬ遅れ | 職場余裕 | 機械待ち、材料待ち、前工程待ち。**本人に原因がない** |
| `中断（内因）` | 避け得る遅れ／休息 | 非作業 | 離席、私語、脇見、休息。**本人由来の停止** |
| `手直し` | （サーブリック外） | 非作業 | やり直し、是正 |
| `その他` | — | — | 最終的な受け皿 |

**設計上の要点**:

- **`手待ち（外因）` と `中断（内因）` を分ける**のは、用途①（ボトルネックの特定）において打つ手が異なるためである（前工程の改善か、作業者への指導か）
- **`検査・測定` を独立させる**のは、サーブリックの分類において帰属が文献間で最も割れている項目であり、上位分類を決め打ちしないためである
- **受け皿ラベルを設けない設計は採らない**。逃げ道がないと、モデルは判別不能な区間を無理に既存ラベルへ押し込み、工程の所要時間が静かに水増しされる

> **注記**: 「第1類／第2類／第3類」という3分類は JIS の規格用語ではなく業界慣用であり、内訳が文献によって4通りに分かれる（特に `検査する` `見出す` `位置決め` `前置き` の帰属）。本書ではこの分類名を採用せず、JIS Z 8141 の作業分類を親カテゴリとして参照するに留める。

### 6.4 粒度の見直し

粒度については**今後の検証で要望があれば見直す**。

### 6.5 汎用性の範囲

プロンプト本体は**同一業種の別工場**まで使い回せることを目標とする。標準書のフォーマットは異なりうるが、組立作業という性質は共通であることを前提とする。

### 6.6 語彙・識別条件の作成契約

標準書PDFからの抽出はセット作成前の独立処理とし、抽出した値を人が確認して公開する。推論ごとのPDF再解釈はしない。PDFのハッシュ、抽出プロンプト・モデル、確認者・日時を記録する。PDFは作成処理時のみ一時アップロードし、抽出結果の永続保存後に削除する。

- 語彙：`{schema_version:"vocabulary.v1",vocabulary_version,non_work_labels_version,source_pdf_sha256,labels:[{job_no,job_title,page_number,kind,standard_duration_s,standard_order}]}`。job_noは文字列・一意、kindは `work / non_work`、時間・順序が標準書に無ければnullとし推測しない。job_titleとの組を固定する。
- 非作業7種は表順に `NW01`〜`NW07` を予約し、`NW07=その他`、page_numberは `-` とする。標準書の番号と衝突したら公開不可として人が対応を確定する。`-` を全非作業の共通キーにしない。
- 識別条件：`{schema_version:"discriminators.v1",discriminator_version,vocabulary_version,source_refs,approved_by,approved_at,conditions:[{job_no,similar_job_nos,observable_features,unknown_when}]}`。各特徴は `{field,criterion}`、fieldはObservationの先頭7項目のキー。観察できる差と、見えない場合に判定しない条件を記す。工程別の条件がない場合も空配列を明示する。
- 条件は標準書・標準動画・開発用動画のみで作り、人が確認する。評価対象のGT・正解理由・手順変動区分を入力資料にしない。全方式のStage2へ同じ条件を渡し、案2だけStage1にも渡す。
- 公開した語彙・条件の版は不変。修正は新しい版とセットIDを発行する（8.7）。語彙一覧はjob_noの文字列昇順で渡し、standard_orderをStage1へ渡さない。Stage2のラベル選択も標準順だけで決めず、順序は出力後の警告に用いる。

## 7. 画面仕様

### 7.1 モード切替

**1画面でタブを切り替える。** タブ名は**業務目的の言葉**で付ける（技術名ではなく）。

**画面を分けない理由**: 第10章の比較が成立する条件は、動画・モデル・リージョン等の条件が2回とも同じであることである。画面をまたぐと設定を入れ直すことになり、条件がずれる余地が生まれる。

**必須の付帯要件**: どちらのモードで出した結果か分からなくなることを防ぐため、**結果ファイルにモードを記録する**（第8.3節）。

タブ名は「お手本なしで分析」（`zero_shot`）／「お手本と照合」（`few_shot`）。初期タブは後者。上部の実動画・標準セット選択の直下、実行ボタンの直前に「分析方式（精度比較用）」の単一選択欄を常時表示し、5.1の名称3件を並べる。初期選択は案1。履歴からの再実行では元の方式を復元する。

説明文：「同じ動画・お手本・設定で方式を変えて比較できます。案1と案3は区間分割を再利用します。案2は区間分割からやり直します。映像を使う案3の再実行には動画の送信と処理費用が発生します。」比較時はモデル・音声・FPS・プロンプト等を固定し、変更項目を実行前の設定要約へ出す。実行中の設定変更は次回だけに適用する。

履歴には日時、Zero/Few、方式、標準セット、モデル、状態、確認対象数、実Stage1 artifact IDと共有元実行、概算費用を表示。「同じ区間でラベルを再判定」操作は互換なキャッシュがある場合のみ有効。案2へ変更した場合は「区間分割から再分析」に変える。画像未生成等で案3が使えなければ理由とセット作成画面への導線を表示し、案1へ黙って代替しない。確認対象には理由、生の確信度、表示用確信度、候補と根拠を表示し、人の修正を別履歴で保存する。

### 7.2 対比タイムチャート

| 項目 | 仕様 |
|---|---|
| 構成 | 上段＝標準作業、下段＝実作業の**2段** |
| 横軸 | **実時間**（絶対時間）。比率での正規化は行わない |
| 動画プレーヤー | **上下段それぞれに配置**し、見比べられるようにする |
| 対応付けキー | **`job_no`** |
| 再生の同期 | **区間同期** — 標準作業の工程 N を見ているとき、実作業の同じ `job_no` の区間へ自動ジャンプする。**独立再生も併用可能とする** |

**横軸を実時間とする理由**: 用途①は「実際に何秒かかったか」を見るものであり、時間を歪める正規化は目的と逆行する。

同じjob_noが反復する場合は、相手段で現在位置以降の最初の一致区間を選び、なければ最初へ戻る。一致なしは「対応区間なし」と表示してジャンプしない。実際に抜けた工程を補って表示しない。Zero-shotでは標準画像・記述を推論に送らないことを上段にも明示する。

### 7.3 長時間処理の扱い

**サーバー側で非同期に処理し、画面は自動で結果を取りに行く。**

- 利用者から見ると「待っているだけ」だが、**ブラウザを閉じても処理は続く**
- Google 公式が長尺動画・複雑なプロンプトに対し `stream` または `background` の使用を推奨している
- 見せかけの進捗表示は廃止する

受付は `202` とrun_idを返し、画面は2秒間隔で状態を取得する。見せるのは「受付／準備／送信／区間分割／ラベル照合／保存／一時ファイル削除／完了」と経過時間。根拠のない進捗率は表示しない。停止ボタンによる明示中断だけをジョブへ伝える。ジョブ状態と削除状態は別表示し、結果が使える場合でも削除待ちを隠さない。APIと永続状態の契約は8.8。

> **既存実装からの転換点（Round 16 で追記）**: 現行の `server.js`（`/api/analyze`）は `response.on("close", ...)` で**接続が切れたら `AbortController` で処理を中断する**設計になっている。本節の「ブラウザを閉じても処理は続く」はこれと**正反対**であり、実装時にはこの中断ロジックを反転させる必要がある。第15章 R7 の「既存疎通確認コードを土台に作り替える」はこの転換を含む。

## 8. データ仕様

### 8.1 動画の保管

| 対象 | 保管場所 | ライフサイクル |
|---|---|---|
| **標準作業動画** | **手元の PC（ローカルフォルダ）に常設** | 手動管理 |
| **実作業動画** | 同上 | 手動管理 |
| **Cloud Storage** | **分析のたびの一時置き場** | **分析後に削除** |

**「ローカルは常設、クラウドは通り道」**という構成である。

**設計上の要件**: 保存・読み出しの窓口を1箇所にまとめ、**保存先を差し替えられる形にする**。将来 Cloud Storage に両方を保管する構成へ、設定変更のみで移行できるようにする。

> Cloud Storage の使用は選択ではなく必須である（第4.2節）。開発者向けモックであっても、バケットが1つ必要になる。

**異常終了時のクリーンアップ（Round 16 で追記）**: 「分析後に削除」は失敗・中断時も含めて保証する（削除の再試行を含む）。第7.3節の非同期処理（ブラウザを閉じても処理継続）と組み合わさるため、正常終了時のみの削除では孤立ファイルが Cloud Storage に残りうる。

**比較セッションの例外**: Stage1プロンプト比較と案1／案3の比較では、実行開始前に比較セッションを作り、同一ハッシュの一時動画をセッション内で再利用できる。後から別ハッシュへ差し替えない。セッション終了・中断・期限切れで削除する。案3のStage2再実行も動画処理費用は発生する。アップロード省略とモデルによる動画再処理省略は別である。

#### 8.1.1 方式別の一時保存と削除時点

| 処理 | Cloud Storageに置くもの | 削除を始める時点 | Stage2だけの再実行 |
|---|---|---|---|
| 標準セット作成 | 標準動画1本（音声設定に応じた派生）、語彙抽出用PDFは別処理 | 各入力を使うAPIが終了し、標準記述／語彙を永続保存した後 | 標準フル動画を再送しない |
| 案1・案2 | 実動画1本、必要な派生動画 | Stage1応答と成功キャッシュを永続保存した後。Stage1失敗なら失敗保存後 | 動画も画像も不要。実Stage1と必要な標準記述のみ |
| 案3 Few-shot | 実動画1本＋標準代表JPEG画像一式 | Stage2応答・結果または失敗を保存し、参照中のAPIが無くなった後 | 実動画と標準画像が必要。削除済みならローカル同一ハッシュから再アップロード |
| 案3 Zero-shot | 実動画1本のみ | 案3と同じ | 実動画が必要、標準画像は送らない |
| 比較セッション | 上記のうち使う資産のみ。参照数で共有 | セッション終了／期限後、参照中の処理終了を待つ | URIを再利用可能だが毎回推論入力として指定する |

テキストJSON、GT、履歴はGEAP入力用バケットへ置かない。標準画像はローカルの永続資産、GCS側は実行時だけの複製とする。すべての一時オブジェクトは `tas-temp/{owner_id}/{session_id-or-run_id}/{asset_id}` の専用prefixに置き、元動画の名前・工程名をオブジェクト名に入れない。

#### 8.1.2 削除台帳と回復（設計既定値）

アップロード前に永続台帳へ `{asset_id,owner_id,run_id,session_id,uri,content_sha256,generation,created_at,expires_at,lease_run_ids,cleanup_status,attempts,next_retry_at,last_error}` を記録する。generationはアップロード後に確定し、それまではnull。書込後・応答前のクラッシュもprefixとasset_idで照合できる。削除は登録されたURI・generationのみを対象とし、バケット全体を走査削除しない。Not Foundは削除成功とする。

通常は最後の参照が解放された時点で削除。APIタイムアウト・中断でリモート終了が確認できなければ `remote_outcome_unknown=true` とし、最後のAPI送信から2時間の猶予リースを置く（実測で見直す設計値、APIの終了保証ではない）。比較セッションは作成から24時間で閉じ、新規処理を受け付けず実行中参照と猶予リースの終了後に削除する。

削除失敗は1分・5分・30分・以後1時間間隔で再試行する。起動時と1分ごとの回収で期限切れ台帳を処理し、24時間未解消なら履歴に `cleanup_failed` と対応要否を表示し、再試行は継続する。結果成功と削除完了は別に記録し、「必ず即時に消える」とは表示しない。補助策として専用prefixに作成後2日のライフサイクル削除を設定し、環境担当が確認する。これは即時削除の代替ではない。

原本の常設動画・標準画像・履歴は自動回収しない。ローカル変換の一時ファイルも同じ台帳で回収する。サーバーを長期間停止しても回収できるようGCSの補助削除を用意し、再起動後は未完了台帳を照合する。

### 8.2 標準作業セット

標準作業セット（動画 ＋ 作成専用GT ＋ Stage1の処理結果・代表画像）を**ローカルに保存し、選択式**とする。標準作業は繰り返し使い回す資産であるため、標準フル動画の毎回のアップロードは行わない。案3の代表画像は8.1に従って一時送信する。

**標準作業側の Stage 1 処理結果は境界固定モードの出力（視覚記述のみ。区間・ラベルは正解ラベル JSON 側が保持する）である**（第5.1節。Round 17 で追記）。実作業側の Stage 1 出力（境界発見モード。区間＋視覚記述）とはスキーマが異なるため、同一スキーマとして扱わないこと。

#### 8.2.1 セットの必須データ（`standard-set.v1`）

`standard_set_id` は公開内容ごとの不変ID（UUID）。変更は新IDと `parent_set_id` を発行する。作成中は `draft / preparing / failed`、生成した全資産の検証後に `ready`、利用停止で `retired` とする。readyは有効な記述profileが1つ以上あることを要求し、選んだ方式に必要なprofile・画像が揃っている場合だけ実行可能にする。以下をmanifestに必須保存する。任意値はキーを省略せずnullで表す。

| キー | 内容 |
|---|---|
| `schema_version,standard_set_id,parent_set_id,name,status,created_at,approved_at,approved_by` | 識別・状態・確認履歴 |
| `source_video` | `{video_id,asset_ref,sha256,duration_s,mime_type}`。asset_refは保存窓口で解決する相対参照 |
| `vocabulary,discriminators` | 6.6の全文と版・内容ハッシュ |
| `build_only_gt` | GT原本への参照、ハッシュ、GT版。**作成／評価専用領域**に置き、通常のAPI入力ビルダーは参照権限を持たない |
| `description_profiles` | `{unguided:descriptorまたはnull,guided:descriptorまたはnull}`。descriptorは固定Stage1 artifact ID、Observation版、固定／発見のプロンプト対の版・ハッシュ、モデル、音声・FPS等の生成条件、検証結果 |
| `examples` | profileごとの `{example_id,segment_id,label:{job_no,job_title},observation}` 配列。作成時にGTとの対応を検証・確認したお手本 |
| `display_segments` | `{segment_id,start_s,end_s,job_no,job_title}`。上段再生用。GT境界に基づき作成するが通常Stage2へ渡さない |
| `representative_images` | 8.2.2の画像manifest配列。未生成は `[]` とし、案3 Few-shotは無効 |
| `provenance` | 作成実行ID、使用原本ハッシュ、抽出・変換ツール版、生成日時、警告、作成規則版 |

推論用ビューは `examples` と語彙・条件のみを明示的に組み立て、セットmanifest全体をJSON文字列で渡してはならない。お手本はjob_no文字列昇順・同ラベル内example_id昇順で並べ、標準動画での時系列を正解順序として渡さない。画像はexampleに紐づけるが、GT原本の工程列・GT境界時刻・作成者の採点注記は渡さない。Observationの観察根拠時刻は残せるが、sourceを標準example内の根拠と明記し、実動画の時刻と混同させない。画像のGT出自は保存領域に保持する。標準GTの通常推論禁止とラベル付きお手本の利用をこの境界で両立させる。

案1・3用記述と案2用記述は別資産とし、足りないprofileを他方で代用しない。3方式の比較用セットは両profileと代表画像を用意する。profile間で変えるのは語彙・識別条件入力だけとし、他の生成条件は揃える。標準固定／実発見に対応する版のプロンプト対が揃っていない、または音声等が異なる場合は比較開始を拒否して再生成を案内する。固定／発見ファイル自体のハッシュ同一は要求しない。

#### 8.2.2 標準代表静止画列（`representative-frames.v1`）

**画像選択は標準側だけで固定し、評価対象動画の正解を見て変更してはならない。** 初期規則 `uniform3.v1` は各GT区間 `[s,e)` の `s+0.2(e-s), s+0.5(e-s), s+0.8(e-s)` の3点。各点以降で最初のデコード可能なフレームを選び、区間内になければ直前の区間内フレーム。同じフレームなら重複除去し1〜3枚とする。空区間・1枚も抽出不能は作成失敗。遮蔽があっても別時刻へ手動選び直さず、そのまま不足として記録する。

EXIF等を除去、回転情報を適用、縦横比維持、長辺768px以下（拡大なし）、JPEGとする。FFmpeg/ffprobeの版、完全な抽出設定・品質値（初期q:v=2）を記録し、実際のPTSを秒で保存する。処理条件の変更は選択／変換規則を改版する。枚数・サイズはモデル上限に収まるか未確認で、Check 11で実測する。超過時に後ろの工程を黙って切り捨てず実行を失敗させる。

画像ごとの必須メタデータ：`image_id,standard_set_id,source_video_id,source_video_sha256,gt_version,gt_process_id,segment_id,example_id,requested_time_s,extracted_time_s,selection_rule_version,transform_version,width,height,mime_type,sha256,asset_ref,created_at`。GT工程IDと区間IDは別に持ち、同一工程の反復を区別する。Stage2へは `image_id,example_id,job_no,frame_order` の対応表と画像Partを送り、元動画の時刻を実動画の時刻として解釈させない。

画像はセット作成時にローカル生成・検証し永続保存する。標準元動画・GT境界・選択規則・変換規則が変われば新セットで再生成。語彙名のみの変更では同一画像バイトを参照できるが、新セットIDと対応メタデータを新規発行する。セット削除はまずretiredにし、新規実行での選択を停止。実行中参照が無くなってから利用者の削除操作でローカル資産を削除し、他セットと共有するバイトは参照数0でのみ削除する。旧履歴・ハッシュ・manifestは残し、媒体削除後の案3再実行は不可と明示する。

既存UI向け9項目はサーバーの表示アダプターで派生する。時刻は表示時のみ秒へ切捨て、duration_secondsは表示用終了秒−開始秒、work_contentとhand_movementはoperation.value（不明なら「不明」）、tools_and_partsはtools_heldとobjects_partsのobserved値を連結する。**採点は小数秒の正本を使う**。旧 `cleanSegment()` を結果正本へ適用するとメタデータが消えるため、将来実装では正本と表示／旧形式エクスポートを分離する。旧形式のみのファイルは再現比較には使わない。

人による編集は `reviewed-result.v1` として元run_id・元結果ハッシュ・編集者・日時・変更前後を保存し、推論結果を上書きしない。自動採用は「確認対象外として表示した」意味で、人が正解を承認した意味ではない。

### 8.4 結果ファイルの蓄積

**結果ファイルは上書きせず、溜めていく。** 比較は利用者がファイルを開いて行う。

### 8.5 中間結果の保存

**Stage 1 の出力を保存し、Stage 2 のみを再実行できるようにする。**

案1・2のStage2再実行には動画再送が不要。案3はStage1を再計算しなくても、Stage2へ実動画・標準画像を再度指定する必要がある。削除済み媒体は再アップロードする。時間・費用差はCheck 11で測る。**2段階構成のメリットは「やり直しの分離」である。**

#### 8.5.1 方式別参照キーと共有実体

`stage1-cache.v1` は、方式別の参照レコードと、不変の応答実体artifactを分ける。これにより `analysis_strategy` を識別子から落とさず、案1・3の同一出力共有を実現する。

`cache_key = SHA256(canonicalJSON(key_fields))`。canonicalJSONは全オブジェクトのキーを辞書順、配列の順序は維持、UTF-8・空白なし・有限数値とし、undefinedを認めず未使用はnullを明示する。key_fieldsには次を**すべて**含める：

- `cache_schema_version,analysis_strategy,stage1_profile`（unguided/guided）、`boundary_mode`（discover/fixed）、`video_id,source_sha256,submitted_sha256,duration_s,preprocess_version`。
- `stage1_prompt_version,stage1_prompt_sha256,observation_schema_version,response_schema_sha256`。
- `vocabulary_version,vocabulary_sha256,discriminator_version,discriminator_sha256,non_work_labels_version,standard_set_id`。案1・3でも比較文脈として記録するが、語彙本文をStage1へ送らない。
- `model_id,model_revision_scope,project,location,host,api_version,processing_mode,audio_enabled,fps,media_resolution,generation_config`。不明なモデル実版は `model_revision_scope` に検証セッションIDを入れ、別セッションで同じ実版とは仮定しない。
- 固定時だけ `boundary_manifest_sha256`、発見時はnull。GTラベルの内容をキーや入力へ混入させない。音声除去・映像回転・フレーム抽出に使うツールの版／設定ハッシュもpreprocessに含める。

参照レコードは `{schema_version,cache_key,key_fields,analysis_strategy,artifact_id,artifact_sha256,producer_run_id,producer_analysis_strategy,reuse_reason,created_at,validation_status}`。artifactは `{artifact_id,stage1_profile,request_sha256,input_signature_sha256,output,raw_response_ref,raw_response_sha256,execution,usage,created_at}`。モデル本文に方式を自己申告させず、サーバーが実行条件から保存する。

**共有規則**：案1と案3のキーはanalysis_strategyだけが異なる。共有候補を探す際はこの1項目だけを除いて一致を確認し、`stage1_profile=unguided`、入力本文ハッシュ・モデル条件・出力スキーマも一致する場合のみ、同じartifact_idとハッシュを指す新しい方式別参照を作る。producer_analysis_strategyは元の値のまま、今回のanalysis_strategyは選択方式の値で記録する。案3を先に実行した場合も同様。同一Stage1比較ではキャッシュミスを黙って再生成せず、一度作成したartifactを両方に明示指定する。

ここでの入力本文ハッシュは `input_signature_sha256` とし、送信本文のmedia URIだけを対応する媒体SHA-256に置換してcanonicalJSON化した値を使う。本文の文字列・並び・設定は変えない。実際の送信JSON全体の `request_sha256` も別に保存する。一時URIの再発行だけで意味が同じ入力を別物と判定せず、媒体が違うのに同じURIだから再利用することも防ぐ。比較キーに入らないrun IDや方式名をStage1本文に差し込まない。

**案2は必ずguided専用artifactを作り、案1・3との共有を禁止する。** Zero/Fewは実Stage1の入力を変えないのでanalysis_modeをキーに含めず同じartifactを使う。選択標準セットの比較文脈は同じにする。

成功・検証済み・完成済みartifactだけを再利用し、部分応答・失敗・固定診断の出力を通常discoverへ流用しない。再試行や反復測定で再生成する場合、同じ入力キーでも新artifact IDを発行し、古い実体を上書きしない。共有先はキーの「最新」ではなくartifact IDまで固定する。

### 8.6 費用

**上限による中断は設けない。記録のみ行う**（第8.3節）。

agentic モードは実行前に消費量を見積もれない。まず実測を積み上げて相場を把握する。上限の要否は相場が見えてから判断する。

### 8.7 変更時の失効と再測定

「失効」は旧成果物を削除する意味ではなく、新条件の推論・比較に流用しない意味。過去結果と旧条件の再現用資産は残す。版番号が同じでも内容ハッシュが変われば設定不正として拒否する。

| 変更 | 標準資産／実Stage1 | Stage2 | 再測定 |
|---|---|---|---|
| 語彙・非作業語彙・識別条件 | 新セットID。guidedは標準固定・実発見とも再生成。unguidedも参照キーは失効するが、入力本文・動画・他条件が完全一致なら明示的な移行記録で旧artifactへ新参照を作成可能 | 全方式再実行 | Check 7〜10、案3は11も。新GTラベル版の採点を固定 |
| Stage1プロンプト／Observationスキーマ | 対象profileの標準記述・実Stage1を再生成。画像はバイト再利用可 | 対象profileの全方式を再実行 | Check 7〜11の対象方式。構造化出力も再確認 |
| Stage2プロンプト／モデル／生成条件 | Stage1は維持。標準記述は維持 | 対象Stage2を再実行 | Check 7・9・10・11。Stage1不変なら8は再集計不要 |
| Stage1モデル／処理モード／音声／FPS／解像度／前処理 | 標準・実Stage1の対象profileを再生成。画像変換も変えた場合は画像再生成 | 下流再実行 | Check 0・1・3〜6の関係部分、新スキーマ、7〜11。Check 2は参考のまま |
| 標準動画・標準GT境界 | 新セット・記述・画像を再作成。実Stage1参照キー失効。入力が変わらない実artifactは明示移行可能 | Fewは再実行。Zeroも比較文脈を更新して新runとして記録 | Check 7〜11 |
| 標準画像選択／変換規則 | 新セットで画像再生成、標準記述と実Stage1バイトは明示移行可 | 案3 Fewのみ再実行。案1・2・Zeroの同条件結果は比較参照可 | Check 11および案3 Fewの7・9・10 |

明示移行は `reuse_reason:"input_equivalent_migration"` と変更前後のキー、同一入力本文ハッシュを保存する。guidedの語彙変更やモデル・音声等の実入力変更には認めない。モデル名が同じでも返却版が変わった場合はモデル変更として扱い、版不明の別日比較は再現性未確認と表示する。

### 8.8 非同期ジョブ・失敗・再試行

#### 8.8.1 APIと永続保存の境界（将来実装の契約）

- `POST /api/media`：ブラウザで選んだファイルのバイト列を逐次受信（Content-Typeは実媒体のMIME、表示名はヘッダーで渡し保存パスには使わない）。サーバーはローカルへ一時保存し、ハッシュ・実MIME・動画長を検証後に常設assetとして登録、`201 {asset_id,sha256,mime_type,duration_s}` を返す。PDFはduration_s=null。動画登録時のasset_idをvideo_idとして使う。原本をブラウザからGEAPへ直接送らない。受信失敗の途中ファイルは回収し、登録完了まで分析受付しない。サーバー側の受信上限・空き容量条件は環境設定として起動時に必須指定し、超過は413／容量不足は507で受付を止める。
- `POST /api/standard-sets`：`{client_request_id,name,source_video_id,build_gt_asset_id,vocabulary_ref,discriminator_ref,profiles,generate_images,settings,parent_set_id,consent_confirmed}` を受け、作成jobとdraftセットを永続化して `202 {run_id,standard_set_id,status}`。consent_confirmed=trueを必須とする。GTの登録は作成専用入口 `POST /api/standard-set-build-inputs/gt` でJSONを検証し保存する（一般media一覧や通常分析の入力候補に出さない）。作成完了後、人の確認を `POST /api/standard-sets/{id}/approve` で記録してreadyへ移す。`GET /api/standard-sets` は公開manifestの表示用項目・利用可能方式を返し、GT原本を返さない。
- `POST /api/comparison-sessions`：`{client_request_id,settings,input_video_id,standard_set_id}` を凍結し、`201 {comparison_session_id,expires_at}` を返す。`POST .../{id}/close` で新規実行受付を閉じる。個々のrunはsessionの設定を継承し、比較軸以外の差を拒否する。共有リースと期限は8.1。
- `POST /api/analysis-runs`：`{client_request_id,input_video_id,standard_set_id,vocabulary_ref,discriminator_ref,analysis_mode,analysis_strategy,settings,stage1_artifact_id,comparison_session_id,parent_run_id,consent_confirmed}`。後ろの参照IDは未指定ならnull、consent_confirmedはtrueが必須。Fewはstandard_set_id必須で語彙・条件はセットと一致させる。Zeroはセット未選択でも確認済み語彙・条件を指定すれば実行できる。全条件をスナップショットして永続化後、`202 {run_id,status,status_url}` を返す。同じclient_request_id・同じ本文は同じrunを返し、同じIDで本文が違えば409。
- `GET /api/analysis-runs/{run_id}`：状態、現在段階、エラー、削除状態、結果の参照、設定要約を返す。認証情報・ローカル絶対パス・GTは返さない。`GET /api/analysis-runs/{run_id}/result` は結果保存後のみ200、それまでは409。
- `POST /api/analysis-runs/{run_id}/cancel`：中断要求を永続化、202。完了済みなら現在状態を返し結果は消さない。`POST .../{run_id}/retry` は新client_request_idを受け、新runとparent_run_idを作る。条件変更を伴う再分析は通常のPOSTを使う。
- ローカルは設定 `DATA_ROOT` 以下の `media/{asset_id}/`、`build-inputs/`、`runs/{run_id}/`、`standard-sets/{id}/`、`stage1-artifacts/{id}/`、`stage1-cache/{key}/`、`cleanup/` に保存。仮ファイルを書いてrenameする単位で更新し、ジョブの状態revisionを増やす。実行ワーカーは初期1並列、同runの二重実行を排他する。共有配置では同等の永続性・排他を持つ保存／キューアダプターへ置換する。

同意確認は動画のGCSアップロード前にも検証し、標準セット作成にも適用する。GT・語彙・識別条件のJSON書式は本書の対応契約で検証する。表示名・任意ローカルパスをファイル操作の指定として受け付けず、発行済みIDから保存窓口で解決する。これらAPIの作成・中断・承認等の状態変更は履歴へ記録する。

#### 8.8.2 状態遷移

通常は `queued → preparing → uploading → stage1_running → stage1_ready → stage2_running → validating → persisting → succeeded`。有効キャッシュがあればstage1_runningを省略、案3はStage2前に必要画像のuploadingへ戻れる。phase履歴に対象assetと段階を保存する。標準作成は別job_kind=`standard_build`で、固定Stage1→画像生成→検証→`awaiting_approval`をたどりStage2は呼ばない。ここでAPI参照は解放し一時媒体を回収、人の承認後にセットready・job succeededへ移す。

| 事象 | 状態と処理 |
|---|---|
| ブラウザ切断 | 状態変更なし。HTTP接続にジョブのAbortControllerを結び付けない |
| 利用者中断 | `cancel_requested → cancelled`。未送信段階は開始しない。実行中通信は中断を試み、サーバー外での処理停止／請求停止は保証しない。保存済みStage1は維持 |
| HTTP 429・5xx | `retry_wait`。同じ入力を初回＋最大2回、5秒・20秒後（Retry-Afterが長いならそれに従う）。各試行の使用量・成否を保存 |
| 401／認証取得不可 | 4.7に従う。回復しなければ `failed` / `AUTH_REQUIRED`。403は権限エラーとして自動反復しない |
| 入力不正・404媒体欠落・構造化出力不正 | `failed`、該当error.codeを保存。自動修正・別方式／別モデルへのフォールバックは禁止 |
| 通信タイムアウト／結果不明 | `failed` / `REMOTE_OUTCOME_UNKNOWN`。重複課金を避けるため自動再送しない。利用者のretryで新run。猶予リースは8.1.2 |
| プロセス異常終了・再起動 | 処理中runを `interrupted` として履歴化。queuedは再開可能、awaiting_approvalはそのまま承認待ちを復元。途中runは完成Stage1等を検証し利用者のretryで続行。結果保存済みならsucceededへ復旧、削除台帳は自動再開 |
| Stage2失敗 | 実Stage1を残す。案1・2は動画不要で再試行。案3は元媒体を要求し、失われていれば `INPUT_UNAVAILABLE` |
| 保存失敗 | 成功にしない。永続Stage1・生応答の存在を確認してからretry。応答が失われた場合は再APIになると記録 |

初期の1回のGEAP呼出しタイムアウトは60分、ジョブ全体は3時間（API待ち・再試行含む。標準セットの人の承認待ちを除く）。承認待ちのセットstatusはpreparing、job statusはawaiting_approvalとし、承認でそれぞれready／succeededへ移す。これは設計の停止条件であり、期待所要時間ではない。Check 11で妥当性を見直し版管理する。完了後に遅れて届いた応答はattempt資料として保持できるが、cancelledや別runの確定結果へ混ぜない。

`cleanup_status` は独立に `not_needed / pending / waiting_lease / deleting / retry_wait / deleted / cleanup_failed`。全終端状態から回収を開始し、結果は成功しても削除失敗なら両方を表示する。履歴と結果は上書きせず、消した媒体の参照には削除日時を残す。処理時間・費用は失敗試行も集計する。

## 9. プロンプト運用

### 9.1 ファイル構成

**プロンプトは外部ファイルとし、版番号を付ける。**

**Stage1は「固定／発見」「unguided／guided」「版」で管理する。** Round 17のモード別ファイルを維持し、単一ファイル内の条件分岐に戻さない。以下は将来作成するファイルの契約であり、今回プロンプト本文は作成しない。

```
prompts/

  stage1_fixed_v1.md             # 案1・3共通、境界固定
  stage1_guided_discover_v1.md   # 案2、境界発見、語彙・識別条件あり
  stage1_guided_fixed_v1.md      # 案2、境界固定、語彙・識別条件あり
  stage2_text_v1.md              # 案1・2共通
  stage2_visual_v1.md            # 案3、実動画と任意の標準画像
  probe_stage1_freeform_fixed_v1.md  # Check 7の自由記述対照のみ
  probe_stage2_freeform_v1.md        # 同上、通常方式には出さない
  ...
```

実行時にどの版・どのモードを使うかを選択できるようにする。

外部設定manifestで、各方式からファイル名・版・SHA-256・応答スキーマへ一意に対応付ける。案1・3のStage1は同じファイルの同じハッシュを参照し、方式名だけの文言もプロンプト本文へ追加しない。比較用Stage2は同じラベル決定・出力制約を持ち、text/visualの差分は媒体入力とその参照規則だけにする。本文変更は版を上げ、標準と実作業の組合せを8.7で失効させる。

初期の処理設定は、動画Partに `mediaProcessing:"AGENTIC"`、`videoMetadata.fps:1`、解像度指定は省略して `api_default` と記録する。Stage1／2のgenerationConfigは `temperature:0` とスキーマ指定、その他は省略を記録し、seedは対応未確認なので指定しない。モデルIDはCheck 6等で確定した設定を必須とし、空なら実行できない。既定値利用は出力の決定性を保証しない。

GEAPへは1段につき実動画全体1本・全区間を1リクエストで扱う。Stage2の案3 Few-shotは全標準exampleの代表画像をimage_id対応テキストと `fileData` のJPEG Partで並べ、最後にタスク指示を置く。実動画Partだけに動画用設定を付ける。文字だけのStage2にmediaProcessingを指定しない。コンテキスト超過・画像数超過・出力打切りは失敗とし、無断の区間間引き・チャンク分割・別モデル化はしない。必要ならCheck 11後に別の設計改訂を行う。

**Git の履歴に任せない理由**: 「v1 と v2 を同じ日に交互に流して比較する」ができないため。履歴を行き来する間に他の条件も動く。

## 10. 評価

### 10.1 方針

- アプリは方式切替・再実行・JSON出力まで作る。GT採点・精度集計は `tools/geap-probe` の将来拡張で行い、並列比較画面は作らない
- 主評価は実作業の推論結果と実作業GT。標準側はセット作成品質を別途点検し、実作業精度へ混ぜない
- 標準・開発・最終評価の動画を分離する。同一撮影の切り出しや同一作業者・製品の近接撮影による偏りもデータmanifestに記録する。別動画であるだけでリークが無いとは断定しない。評価GTを見て標準画像・識別条件・閾値を調整することを禁止する

> **注意**: 実作業の正解ラベルを Zero-shot 出力から作る場合、**人による修正を必ず挟むこと**。未修正のまま正解として採用すると、評価が「Few-shot 結果と Zero-shot 結果の一致度」を測るだけになり、精度評価として機能しない。

### 10.2 指標

**TAS の標準指標セットに、実務指標を加える。**

#### 10.2.1 標準指標（論文・他社事例との比較用）

MS-TCN / MS-TCN++ / ASFormer がいずれも同一実装で報告している事実上の標準である。

| 指標 | 定義 |
|---|---|
| **Acc（MoF）** | フレーム単位の正解率。テストセット全体でフレームをプールする micro 平均。背景クラスも分子・分母に含める |
| **Edit Score** | 区間ラベル列（時刻は破棄）に対する Levenshtein 距離（挿入・削除・置換のコストは全て1）。`Edit = (1 − 距離 / max(\|予測\|, \|正解\|)) × 100`。**動画ごとに算出して動画数で平均（macro）** |
| **F1@10 / F1@25 / F1@50** | 数字はIoUのしきい値（%）。予測を時間順に走査し、同ラベルの最大IoUのGTが未使用かつ閾値以上ならTP、他はFP。使用済みなら第2候補に付け替えない（10.3）。**各GTは1回のみマッチ可能**。TP/FP/FNを全動画で合算して `2TP/(2TP+FP+FN)` を算出（micro） |

#### 10.2.2 実務指標（本件で追加）

| 指標 | 定義 | 追加理由 |
|---|---|---|
| **IoU（区間単位）** | 対応づいた区間ペアごとの IoU の平均 | 「検出できた工程がどれだけ正確に重なっているか」 |
| **IoU（クラス単位）** | ラベルごとに、そのラベルの全時間で IoU を算出しラベル平均 | **どの工程が苦手かが分かる**。プロンプト改善に直接効く |
| **境界誤差（秒）** | 対応づいた区間の境界誤差の**中央値と95パーセンタイル**、および工程ごとの所要時間の絶対誤差 | **標準指標は境界精度をほぼ捉えないため**（10.2.3） |
| **語彙外率** | 語彙に無いラベルを出力した割合。**0% であるべき** | 第1目的（ラベルの統一）を直接測る |
| **受け皿ラベル率** | `その他` の割合。高すぎ＝取りこぼし、低すぎ＝無理な当てはめ | 同上 |
| **MoC** | 工程ラベルごとの正解率の単純平均 | MoF は長い工程に支配され、**短い工程が全滅していても高く出る** |
| **類似工程サブセット精度**（Round 16 で追加） | GT 上で「視覚的に類似した工程が連続する区間」だけを切り出して算出した Acc・Edit・F1 | 第5.4節：R11 により設計（フル動画2本）は撤回されたが、R11 が答えていなかった R5 の懸念（長くて類似した作業を Stage 1 単体で切り分けられるか）を実測で決着させるため（Round 17 で表現を修正）。区間の選定基準（何をもって「類似」とするか）は実装時にGT作成者が明記する |

類似工程は**連続区間だけでなく、離れた位置での反復も対象**とする。グループは開発集合で視覚的差を列挙して事前に固定し、評価結果を見て苦手な工程を除外しない。連続場面のAcc/Edit/F1は事前定義した時間窓をそれぞれ独立の動画として評価し、離れた場面を連結して架空の隣接境界を作らない。非連続工程は全出現のMoC・混同行列も併記する。

**語彙外率0%は必要条件にすぎない。全区間を語彙内の別工程へ割り当てても0%になる。** 次を必須追加する（採点用GTはモデルへ渡さない）。

| 指標 | 分母・対応方法 |
|---|---|
| 語彙内の別工程への誤割当率 | GTと予測のラベルが異なり予測が語彙内である評価フレーム数／全評価フレーム数。その他への誤りも含む総数と、その他を除いた取り違えを別記 |
| 固定境界の区間ラベル正解率 | Check 7の入力GT区間数が分母。job_noとjob_titleの組が一致した数／区間数。MoCは工程別のこの正解率の平均 |
| 類似工程グループ別混同行列 | 行=GT工程、列=予測工程＋その他＋invalid。Check 7は区間数、通常運用はフレーム数。グループ外への誤割当を列から除外しない。件数と行正規化率を併記 |
| 警告されない誤り率 | Check 10の「自動採用区間内の誤り率」と「全区間に占める見逃し」を両方表示。分母を省略しない |
| 同ラベル内の余分な切れ目 | 生Stage1の区間数・Check 8の余分な境界と分裂。TAS標準指標の同ラベル圧縮前に測る |

語彙外率・その他率は区間数ベースとフレームベースを併記し、語彙外は受理前の生出力でも測る。契約違反の試行を「失敗だったので精度集計から消す」ことは禁止する（10.6）。

#### 10.2.3 標準指標だけでは不十分な理由

公式実装のアルゴリズムを再現し、本件条件（20分・40区間）で確認した結果である。

| 誤りの種類 | Acc | Edit | F1@10 | F1@50 |
|---|---|---|---|---|
| 完璧 | 100 | 100 | 100 | 100 |
| **全境界が区間長の30%ずれる** | 70.8 | **100** | **100** | **100** |
| 全境界が区間長の70%ずれる | 31.8 | **100** | **100** | 2.5 |
| 全区間に細かいノイズ（過分割） | 93.3 | 33.3 | 50 | 50 |

**Edit Score と F1 は境界のズレに対してほぼ盲目である。** 30秒の工程なら9秒、3分の工程なら54秒ずれていても満点になる。用途①（山積み表）は工程ごとの所要時間の分布を見るものであり、標準指標が満点でも山積み表が使い物にならない状態が起こり得る。

3指標の役割分担は以下の通りで、**互いに直交しており、どれか1つでは必ず抜け穴ができる**。

| 指標 | 捉えるもの | 捉えないもの |
|---|---|---|
| Acc | 境界のズレ量（**唯一これに反応する**） | 過分割 |
| Edit | 工程の順序と個数（過分割に最も敏感） | **境界精度に完全に盲目** |
| F1@k | 各工程を1対1で検出できたか | 境界精度（しきい値をまたぐまで無反応） |

> 上記の数値は公式アルゴリズムを再現して合成データで測定したものであり、論文記載の数値ではない。**このシミュレーションコードは本書に含まれておらず、保存場所が未記録である**（Round 16 で追記）。将来の実測値と乖離した際に切り分けができるよう、実装時にコードを `tools/` 以下等へ保存し、本書から参照できるようにすること。

### 10.3 評価プロトコル（`tas-eval.v1`、設計として確定）

1. **時間軸**：動画先頭0の秒、半開区間。フレーム指標は10Hzの `t=n/10, 0<=t<duration_s` でラベル化する。これは評価のサンプリングであり、GEAP入力FPSとは別。動画長はffprobe取得値、GTは全長を隙間なく覆う。時刻丸め・±秒の正解救済は主指標で行わない。
2. **標準区間列**：フレーム列から隣接同一ラベルを圧縮してEdit/F1を算出。非作業7種は除外しない。圧縮前の生Stage1区間ID列をCheck 8・10用に必ず保持する。
3. **Edit**：10.2.1の式、動画macro。両方空の採点はしない（動画長0は入力不正）。失敗出力は10.6の規則に従う。
4. **F1**：各予測区間を時系列走査し、同ラベルGT全件から最大IoUを選ぶ（同値なら早いGT）。そのGTが未使用かつIoU閾値以上ならTP、そうでなければFP。使用済みなら第2候補へ付け替えない。未使用GTはFN。10/25/50ごとに独立計算、全動画でTP/FP/FNを合算する。類似工程の連続時間窓でも同じ算法を使う。
5. **区間IoU・境界・時間誤差**：F1@50で成立したペアを流用する。ペア数、GT数、マッチ率を必ず添え、未対応を誤差0にしない。区間IoUはペア平均、開始・終了絶対誤差をまとめ中央値／p95、所要時間絶対誤差も中央値／p95で出す。ラベルに依存しない境界診断はCheck 8で別計算する。
6. **クラス集計**：MoCは全評価集合のGTに出現するクラスだけでクラス別フレーム正解率を平均。クラスIoUはGTまたは予測に出現したクラスの和集合で平均（予測だけのクラスは0）。両方に無いクラスはnullとして除外し除外数を記録。動画ごとの平均と混同しない。
7. **緩和診断**：境界の許容幅は1秒・3秒・5秒を別表で出し、主設定は3秒。主精度の書換えには使わず「緩和評価」と明記する。主指標と許容幅別の値を混ぜない。
8. **集約**：標準指標のmicro/macroは10.2.1の通り。率は必ず分子・分母と対象動画数を出す。分母0はnull（N/A）であり100%や0%にしない。p95は昇順のnearest-rank `ceil(0.95N)` 番目、中央値は偶数なら中央2値の平均。反復間平均・最小・最大・標準偏差も保存する。
9. **GT一貫性**：評価担当は判断基準・境界事例集・曖昧ラベル処理を版管理。GT全件を人が確認し、独立した第2確認者が各手順変動区分の20%以上と全曖昧区間を再注釈する。ラベル一致率と境界差、裁定履歴を保存し最終GTを凍結する。内因／外因等が動画だけで不明なら、見えていない根拠をモデルに期待せず、映像識別可能／不能の採点区分も残す。

JSONの率（Acc、F1、IoU、MoC、各種誤り率）は0〜1で保存し、画面・表で%表示するときだけ100倍する。Edit Scoreのみ式どおり0〜100。採点ポリシーの閾値にも単位を記録する。F1用の圧縮区間はフレームindexの開始／終了（終了は排他的）を保持し、秒表示は開始index/10、終了min(duration_s,終了index/10)とする。項目5の境界誤差もこの評価区間から計算し、生の小数秒境界の誤差はCheck 8で別に出す。

参照はMS-TCN著者公式 `https://github.com/yabufarha/ms-tcn` の `eval.py`。**採用コミットハッシュは未確認で、検証実装前に記録する**。今回の定義・非作業扱い・生境界診断による差分も併記し、外部論文との完全同条件比較とは呼ばない。境界0始まり／終端の扱いを小さな手計算例で確認してから実測する。

### 10.4 非作業ラベルの扱い

**非作業ラベル（第6.3節）を評価対象から除外しない。**

用途①はボトルネック工程の特定とばらつきの発見であり、**手待ちや段取りこそが見つけたいムダそのもの**である。これを評価から除外すると、最も重要な部分の精度を測らないまま判断することになる。

### 10.5 合格ライン

**`語彙外率 = 0%` を除き、検証で相場を掴んでから確定し、本書に追記する。**

現時点で測定値がゼロであるため、いま引く線は根拠のない数字になる。語彙外率のみ、程度問題ではなく明確な不具合であるため先に確定する。

初期の確認閾値0.70等（5.3）は振り分けの設計値であり、ここでの精度合格ラインではない。予備測定後に `acceptance-policy.v1` へ、類似工程群／手順変動群の最低精度、結合・分裂・欠落の上限、警告されない誤り率の上限、自動採用率の下限、確認対象率・時間・費用の上限、案3に求める改善幅と許容悪化幅を記入する。**全件を低確信度・その他にして合格する基準は禁止**。未記入の項目があればMEASUREDに留め、PASSにしない。閾値・採用方式・根拠・確認者・日付を独立評価の前に固定する。

### 10.6 方式／Zero-shot・Few-shotの公平な比較

| 比較軸 | 意図的に変える条件 | 固定する条件 |
|---|---|---|
| 案1 vs 案3 | Stage2の映像根拠だけ | **同一の実Stage1 artifact ID・ハッシュ**、同じunguided標準記述、語彙・識別条件、下記共通条件 |
| 案1 vs 案2 | Stage1の語彙・識別条件入力（標準／実とも） | 同一Observation定義、固定／発見規則、Stage2 textプロンプト、標準動画・GT境界・例示件数。Stage1 artifactは別であることを検査 |
| 各方式内のZero vs Few | 標準記述、案3では標準画像も含む「お手本の有無」 | **実Stage1は共有**、両方に同じ語彙・識別条件。Zeroへの標準情報漏れを入力manifestで検査 |
| Check 7 自由記述 vs 案1 | Stage1記述の形式とそれを読むStage2の最小差分 | 正解境界・語彙入力なし・モデル・お手本の範囲・他の全条件。自由記述用派生プロンプトを凍結し原本は使わない |
| Check 11の3条件 | Stage2の実動画・標準画像の有無だけ | 同じ実Stage1、同じ標準記述・例示順・語彙・識別条件・モデル・時刻・安全網 |

共通の固定条件は、実動画原本／送信バイト・動画長、標準セットIDと構成ハッシュ、Zero/Few、両Stageのモデル・返却版、project/location/endpoint/API版、処理要求モード、音声・FPS・解像度、全generationConfig、Observation／出力スキーマ、プロンプト版・ハッシュ、語彙／識別条件／非作業版、画像選択／変換規則と画像ID順、例示数・順序、安全網版、評価GT・評価プログラム版、同意・保存条件とする。方式が必然的に変えるものは上表の差分として明示し、「同条件」の名の下に隠さない。要求agenticに痕跡がない実行は別層 `agentic_unconfirmed` へ分け、agentic比較の成功例に混ぜない。

**実験単位**は動画×条件×反復。開発集合と独立評価集合を分け、最終評価は各条件3反復（反復ID 1〜3）。各反復で実Stage1を新規生成し、その反復内の案1／3・Zero/Few・Check 11条件は同じartifactを使う。標準資産は全反復で固定する。反復順は条件リストを反復ごとに1つ循環させ、順序をmanifestに保存する。混同行列は各反復と合算を区別し、動画数が3倍になったと見なさない。

比較は同じ動画・同じ反復で差を取り、反復別の差・平均・最小・最大を報告する。母集団精度の保証はしない。20分運用の時間は、Stage1生成を含む初回総時間、同Stage1を使うStage2再実行時間、標準セット作成の一回限りの時間を分ける。キャッシュ共有の生成費用を全方式が消費したように重複請求集計せず、実支出と「各方式を単独で実行した場合の帰属費用」を別欄で出す。

構造不正・通信失敗・中断は件数と完了率を全予定実行数を分母として報告する。構造不正の全出力は主評価用に全動画 `__INVALID__` ラベル1区間を置き、Acc・Edit・F1は0、自動採用0、確認対象は全動画として記録する。これは採点上の失敗表現であり、生の語彙外率は読み取れるラベルから別計算する。ラベルすら取得できなければ生の語彙外率はnullとし、失敗を語彙外0%にしない。部分成功を抜き取らない。通信失敗／中断は精度N/Aとし、完了例だけの精度と、失敗動画の正解フレーム数を0とした実施済み全条件の実効Accを併記する。未実施は成功にも失敗にも数えず予定残として表示し、実効Accの分母にも含めない。予定残のある区分は合格にしない。

### 12.4 Check 7：正解境界を与えたときの文章照合成立性

**目的**：分割誤りを取り除いて、文章だけで類似工程を区別できるかを測る。これは診断値であり通常推論精度とは別表にする。状態は**未実装・未実施**。

**手順（追加関数 `checkFixedBoundaryMatching`）**：

1. 標準セットの同一GT境界に対して、自由記述／unguided項目化／guided項目化の固定Stage1を用意する。自由記述は診断用派生プロンプトで `description` 一文形式と自己申告・根拠を出す。標準のお手本ラベルは作成処理でのみ対応付ける。
2. 実動画の匿名GT境界を用い、自由記述、案1、案2の固定Stage1を別々に実行する。案2だけ語彙・識別条件をStage1へ渡す。案3には**案1と同じ固定Stage1 artifact**を指定する。固定応答の全ID一致を検証し、サーバーで入力境界を結合する。
3. 同じ語彙・識別条件・標準セット・モデル・条件で、自由記述＋文章Stage2、案1、案2、案3を実行。Zero/Fewの両方を10.6に従って測る。案3 Fewだけ実動画＋標準画像、案3 Zeroは実動画だけ。自由記述は `analysis_strategy:"text_only",description_format:"freeform_control"` と診断専用cache namespaceを保存し、通常の項目化結果と混ぜない。
4. 採点関数にだけ実GTラベルを読み込ませ、区間完全一致正解率、区間MoC、グループ別混同行列、語彙外率、その他率、Check 10の指標を出す。失敗・誤りID・候補・根拠の参照先を保存する。

標準側・実側のobserved項目数、unknown率、自己申告率も並べる。自由記述には項目別unknown率を捏造せずN/Aとする。文章条件で誤り、映像条件で正解になった区間は人が文章だけ／動画ありの順で確認する。人の判断は原因診断として別記し、理論上限とは呼ばない。

### 12.5 Check 8：Stage1の工程結合・分裂と固定区間の限界

**目的**：時刻の小さなズレと、ラベルを付け直しても戻せない分割誤りを分ける。状態は**未実装・未実施**。追加関数 `checkSegmentationStructure` はCheck 9の通常discover成果物を再利用し、採点自体にAPIを呼ばない。案1／3は同じ結果、案2は別結果を示す。

GTの各出現区間をG、予測の生区間をP、重複秒数を `O[p,g]=max(0,min(p.end,g.end)-max(p.start,g.start))` とする。ラベル圧縮前のIDを使い、同じjob_noの反復も別GT出現として扱う。

| 指標 | 実装規則 |
|---|---|
| 異種工程の結合 | 1つのPに、異なるGT job_noの区間が2つ以上、実質重複しているP数／全P数。実質重複は `O >= min(1秒,0.1×min(P長,G長))`。全正重複O>0の厳密版も別出力し、軽微な境界越えと区別 |
| 同一工程の分裂 | 1つのGT出現Gに実質重複するPが2個以上あるG数／全G数。超過数 `sum(max(0,countP−1))` も出す。後段で同ラベルが付いても生境界では分裂として残す |
| 工程欠落（対応区間なし） | 正の重複を持つP-Gを時系列順・1対1で対応させ、まず対応数最大、次に総IoU最大の動的計画法を用いる。同値は早いID列。未対応GT数／全GT数を欠落候補、未対応Pを余剰区間として出す |
| 結合に隠れた工程 | 上記未対応GTのうち結合Pに実質重複するものを別数で出す。「動画を全く見落とした」と断定せず、独立区間として表せていないと解釈 |
| 内部境界の対応 | 0と動画終端を除く境界を重複除去。許容1/3/5秒ごとに、距離が許容以下の組で時系列1対1、対応数最大→総絶対誤差最小→早い時刻列の順でDP対応。1予測を複数GTへ使わない |
| 欠落境界・余分な境界 | 未対応GT境界数、未対応P境界数。検出率=対応数／GT内部境界数、適合率=対応数／P内部境界数、対応済み絶対誤差の中央値／p95を併記 |
| 工程別の時間誤差 | ラベル非依存のP-G対応について開始・終了・所要時間の絶対誤差を出す。通常ラベル一致ペアの10.3とは別表 |

「欠落候補」は幾何的な区間対応の定義であり、真の作業の非観察や誤ラベルとは区別する。通常推論の工程抜け警告（標準語彙にあるのに出現しない）とも別指標。結合・分裂・欠落候補は重なるので合算を総誤り数にしない。

**Stage2が理想的な場合の上限**：10.3の同じ評価フレーム集合を使い、予測区間pに入るGTラベルlのフレーム数を `N[p,l]` とする。`oracle_MoF = sum_p max_l N[p,l] / 全評価フレーム数`。各pへ最頻GTラベル1つを割り当てる（同数ならjob_no昇順）。これは**固定区間に一つのラベルだけを付ける条件でのMoF上限**であり、Edit/F1/MoCの同時上限ではない。連続時間版も `sum_p max_l sum_{g:label=l} O[p,g] / 動画長` として別に出す。不正な重複区間のまま計算しない。Stage1不正ならoracleはnull、契約失敗を記録する。

受入用手計算例：GT A=[0,10), B=[10,20)、予測P=[0,20)なら異種結合1、oracle_MoF=0.5。GT A=[0,20)、予測=[0,10),[10,20)なら分裂1、余分な内部境界1、oracle_MoF=1.0（分裂をMoFだけでは見つけられない）。

**判定**：固定区間の上限自体が最低必要精度を下回ればStage2だけの改善で採用しない。各率・境界誤差は閾値確定までMEASURED。Check 5を代用しない。

### 12.7 Check 10：安全網の実効性

状態は**未実装・未実施**。追加関数 `checkSafetyNet` はCheck 7・9・11の保存出力を採点し、**APIは再呼出ししない**。5.3の安全網を人による修正前のモデル結果へ適用する。

**区間誤りの定義**：Check 7は固定区間の正解ラベルとの完全不一致。通常運用は各予測区間pについて、予測ラベルと一致しないGT時間を `wrong_seconds[p]` とし、0より大きければ `E[p]=1`、完全一致なら0とする。ラベル誤りと境界越えを両方捉える厳密定義なので、補助的に「最長重複GTラベルとの不一致」も別欄で出す（同時間はjob_no昇順）。主指標のEを事後に多数決へ変更しない。

`R[p]=review_required`、`A[p]=!R[p]`、全予測区間数をNとする。5.6の動画単位警告は全区間へRを立てる。実Stage1自己申告、参照標準の自己申告、同着・強制低下、通常の低確信度、その他、品質警告を別フラグで保存し、複数フラグの重複を保持する。

| 指標 | 計算 |
|---|---|
| 誤り検知率 | `sum(E×R) / sum(E)`。全誤りのうち確認対象へ回せた割合 |
| 警告されない自動採用区間の誤り率 | `sum(E×A) / sum(A)`。最も重要な見逃し指標 |
| 全区間に占める警告されない誤り率 | `sum(E×A) / N`。上段と分母が異なるので別名で出す |
| 自動採用率・確認対象率 | `sum(A)/N`、`sum(R)/N`。時間ベースも区間長で重み付けして出す |
| 確認対象の的中率 | `sum(E×R)/sum(R)`。確認負担を解釈する補助指標 |
| 自動採用部分の誤り秒率 | `sum(wrong_seconds×A) / sum(duration×A)`。長い結合区間を件数だけで過小評価しない |
| 確信度帯ごとの正解率 | confidence_rawを `[0,.1),[.1,.2),…,[.9,1]` に分け、各帯の `sum(1−E)/件数`、件数、平均raw、GT時間一致率を出す |

生の確信度帯は、①全件、②forced_low_confidence=falseだけ、③強制低下対象だけを別表で出す。表示用confidenceの分布は別表とし、生の分布へ混ぜない（Round 17維持）。**安全網全体の検知率から強制低下対象を除外しない**。

要因別は `stage1_insufficient`（実／標準を分ける）、`forced_low`、`ordinary_low` を最低限別々に集計する。各要因の対象数・誤り数・その要因だけで検知した数と、全要因の和集合を出す。重複があるため要因別件数を足して全体検知数にしない。構造不正は全動画確認対象、通信失敗は区間指標N/Aとし、10.6の完了率と併記する。

**判定**：見逃し率上限・自動採用率下限・確認対象率上限を同時に満たす必要がある。予備測定で閾値を調整したら安全網版を上げ、独立評価では固定する。誤り0または自動採用0等で分母が0ならN/A、満点として合格させない。
