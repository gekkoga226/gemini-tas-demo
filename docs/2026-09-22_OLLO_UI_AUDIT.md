# 結論

監査日：2026-09-21〜22（JST）／公開情報の追加確認・HTMLモック作成：2026-09-22。

最優先は次の3件です。いずれも現行の「作業みえる」の監査結果であり、Ollo製品そのものに同じ不具合があるという意味ではありません。

1. **開始条件をモード別に説明する（P1）**。「お手本なし」でもお手本を選ぶ表現が残り、再生用ファイル選択と分析への入力が区別しにくい状態です。初心者が必要な準備を誤解し、分析開始まで迷います。
2. **お手本なしの結果を、比較が成立していない比較画面にしない（P1）**。隔離したローカル検証では標準セットなしの完了画面に「お手本0本」の集計と同一結果同士の差分0が出ました。「差がない＝良好」と読まれるおそれがあります。
3. **動画・時間軸・選択区間の根拠を近づける（P1）**。完了後の遷移先から集計を経て確認用動画に到達するまで長いスクロールが必要です。映像と結果を往復する負担が大きく、未確認区間を確認し終える導線も弱くなっています。

改善のHTMLは[画面一覧](ui-audit-2026-09-21/index.html)にまとめました。Olloの公開UIで確認した「動画を主領域に置き、直下に時間軸、右側に詳細を置く」配置を強く参考にしています。Tools相当は動画1本、Training相当は2本とし、開始・分析中・確認作業を分けています。本体の実装は変更していません。

# 画面・フロー別監査

本書のToolsは「お手本なし／zero」、Trainingは「お手本あり／few」の体験比較に使う区分です。Olloの製品機能と本リポジトリの推論方式が同一だという対応付けではありません。P0＝主要作業の全面停止・重大なデータ損失、P1＝主要フローの誤解や大きな障害、P2＝局所的な負担・改善機会。今回P0と断定できる証拠はありません。

## Tools：お手本なしで開始し、観察結果を確認する

### T1：分析に必要な入力と、再生用の選択が混同しやすい

- **問題**：zeroモードにも「お手本を選ぶ」系の表現があり、「お手本がなくても開始できるのか」「作業名一覧は必要なのか」が一読で分かりません。
- **根拠**：**画面・コード確認済み**。[analysis.html:37](../public/analysis.html#L37)、[fewshot.js:25](../public/fewshot.js#L25)。ホームの参照ファイル操作は[work-app.js:97](../public/work-app.js#L97)でファイル名・サイズの扱いが中心で、分析への登録とは別です。
- **ユーザーへの影響**：準備不足の発見が遅れ、再生する動画を選んだだけで分析入力を設定したと思い込みます。
- **重要度**：P1。
- **改善案**：「対象動画」「確認済みの作業名一覧」「同意」の3条件を表示。お手本動画は不要であること、語彙は何に使われるか、開始後に得られる結果を明示。CTAを「作業の分析を開始」にします。
- **既存スタックでの実装方針**：既存フォームとmode状態を維持し、ラベル・補助文・入力必須条件を切り替える。ファイル選択時の状態を「再生用」「分析に登録済み」で区別。3案の選択は隠さず残します。
- **確認方法**：初見利用者にお手本なしで開始する課題を出し、説明なしで入力とCTAに到達できるか確認。モード往復で未送信入力が消えないこと、zeroで参照動画・記述を送信しないことを検証します。

### T2：比較対象がない結果に、お手本集計と自己比較が出る

- **問題**：単独動画を理解する前に、成立していない比較情報を読ませています。
- **根拠**：**ローカルmock画面・コード確認済み**。標準セットなし／語彙ありでzeroを完了すると、`#resultAnalytics` に「お手本の時間を見比べる」「0本」が表示され、空の分布と同一結果同士の差分0が出ました。[fewshot.js:119](../public/fewshot.js#L119)、[standard-charts.js:6](../public/standard-charts.js#L6)。
- **ユーザーへの影響**：結果未生成と比較対象なしを区別できず、差分0を性能評価として受け取る可能性があります。
- **重要度**：P1。
- **改善案**：最初は動画1本、作業区間、所要時間、観察根拠、未確認区間を表示。比較を提供する場合は異なる比較対象を明示的に選んだ後に表示。「対象なし」は次の操作を示す空状態にします。
- **既存スタックでの実装方針**：集計描画にmodeと比較対象の有効性を渡し、同一run同士・空標準の自動比較を防ぐ。既存結果データと時間計算は変えず、表示条件を分離します。
- **確認方法**：zero／few × 標準0・1・複数本 × 結果0・1・複数件で表示を確認。値0、欠測、比較不能を別表示とし、架空の標準時間を補完しないことを確認します。

### T3：区間選択後にキーボードフォーカスを失う

- **問題**：一覧の再描画で操作中の要素が置換されます。区間番号の文字コントラストにも不足があります。
- **根拠**：**操作・コード確認済み**。ホームの4番目の `.segment-row` をEnterで選択すると、インスペクタは更新されますが `document.activeElement` はBODYになりました。[work-app.js:40](../public/work-app.js#L40)の一覧描画と[同:50](../public/work-app.js#L50)の選択処理。`.row-index` の12px、`#8b94a3` は白背景との比約3.06:1、選択背景 `#f0f3fa` では約2.75:1です。
- **ユーザーへの影響**：連続した確認にマウスが必要となり、現在位置を見失います。小さい番号が読み取りにくくなります。
- **重要度**：P1。
- **改善案**：選択要素を維持するか、再描画後に同じ区間へフォーカスを戻す。通常の小文字は4.5:1以上とし、選択を色だけに頼らず境界線と状態でも示します。
- **既存スタックでの実装方針**：安定した区間IDを用い、選択DOMのクラス更新を優先。再描画が必要な場合だけフォーカス復元。共通CSS色変数を調整します。
- **確認方法**：Tab→Enter→次のTab、検索後の選択、最終区間、選択区間の非表示化を確認。白・選択・hoverの各背景でコントラストを計測します。[WCAG Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

## Training：お手本を選び、対応する工程の違いを確認する

### R1：完了後の最初の確認作業より、集計の表示が先に続く

- **問題**：動画と結果の対応を確認する前に長い集計領域を通過します。集計用の比較動画と編集用の動画が重複しています。
- **根拠**：**画面・コード確認済み**。[analysis.html:91](../public/analysis.html#L91)、[standard-charts.js](../public/standard-charts.js)。ローカルmock、viewport 1171×912で完了リンクの遷移先workspaceは上端y=76、集計領域の高さは約1973px。集計内プレイヤーのyは約1240、別の標準・対象プレイヤーは約2240・2716でした。座標はその検証データと表示条件の計測値です。
- **ユーザーへの影響**：映像・時間差・根拠を記憶しながら往復する必要があります。分析完了が、確認作業の開始につながりません。
- **重要度**：P1。
- **改善案**：デスクトップは左右の動画を主領域、その直下に2段の時間軸と選択区間の根拠、右側に区間一覧。集計は切替表示にし、完了CTAを「未確認の区間から見る」にします。
- **既存スタックでの実装方針**：既存video・timeline・editorをCSS Gridで再配置し、選択区間を共通状態にする。動画インスタンスの重複を整理します。現在の仕様7.2が示すプレイヤーの上下配置から左右配置への変更は、**仕様更新を伴う提案**です。時間軸の実時刻は保持します。
- **確認方法**：1区間の根拠確認で必要なスクロール回数・クリック数・所要時間を現行と比較。1366×768と1920×1080で選択区間、動画、時間差の同時確認を試します。分布・作業名別集計が失われないことも確認します。

### R2：「同期」が何をするか分かりにくい

- **問題**：対応工程へのジャンプと、動画の再生・停止を連動する同期を区別する説明が不足しています。
- **根拠**：**コード確認済み**。[fewshot.js:153](../public/fewshot.js#L153)の `syncFrom` は `job_no` を手がかりにcurrentTimeを移動。集計の比較も該当工程の位置への移動と個別の再生が中心です。全再生操作がリンクすることは確認できません。
- **ユーザーへの影響**：同じ絶対時刻・同じ工程・同じ進行率のどれを比較しているか誤解し、時間差の解釈が揺れます。
- **重要度**：P2。
- **改善案**：まず「対応工程の先頭へ移動」「再生は個別」と挙動どおり表示。将来の連動再生は、同時再生と工程合わせを区別して提供します。
- **既存スタックでの実装方針**：既存の対応関係とcurrentTime操作を利用。表示用の再生位置と推論区間時刻を分離し、同期操作でStage2の時刻を書き換えません。
- **確認方法**：工程の欠落・繰り返し・長さの違い・複数候補・動画終了で、移動先とラベルが一致するか検証します。[Frame.io比較ビュー](https://help.frame.io/en/articles/9952618-comparison-viewer)

### R3：処理状態はあるが、完了・失敗・通信断の次の操作を強めたい

- **問題**：状態表示自体は実装されていますが、「今待ってよいか」「結果を見るか」「再接続を待つか」の主操作をさらに明確にできます。状態領域全体の読み上げが反復される可能性もあります。
- **根拠**：**コード確認済み**。[analysis-state.js:2](../public/analysis-state.js#L2)、[run-observer.js:2](../public/run-observer.js#L2)、[analysis.html:54](../public/analysis.html#L54)。ポーリング、経過表示、一時媒体回収の区別は存在。`aria-live="polite"`・`aria-atomic="true"` の領域で経過時間も更新されます。**読み上げの実際の反復は未確認**。
- **ユーザーへの影響**：処理完了と媒体削除完了を混同し、結果確認を待ち続ける可能性があります。通信断を処理中止と誤解するおそれもあります。
- **重要度**：P2。
- **改善案**：入力確認→区間分割→照合→保存の段階を表示。分からない残り時間・百分率は作らない。完了、再接続中、失敗、中止ごとに主CTAを変え、媒体回収は独立表示します。
- **既存スタックでの実装方針**：既存サーバー状態を正本として表示用状態へ対応付ける。live regionは状態変化だけを通知し、秒単位タイマーを外す。再試行は別runとして原本を保持します。
- **確認方法**：ネットワーク遮断、再接続、429/5xx、失敗後再試行、中止、完了後の媒体削除待ちを検証。NVDAなどで重複・欠落通知を確認。[Status Messages](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)

### R4：モバイルで縦方向の距離がさらに増えるおそれ

- **問題**：デスクトップの複数領域を1列にするだけでは、比較・編集の往復距離が増えます。
- **根拠**：**コード確認済み／現行実端末未確認**。`analysis-refinement.css`（監査時点のファイル。段階3で削除済みのためリンクなし）の1000px・720px付近の条件で、集計・動画・時間軸・編集などが1列になります。現行アプリの端末幅固定操作は確認を完了できていません。モバイルでの障害を実測事実とはしません。
- **ユーザーへの影響**：映像を見た後に結果までスクロールし、選択した工程の位置を見失う可能性があります。
- **重要度**：P1（構造からのリスク評価。実機確認後に再判定）。
- **改善案**：映像は「お手本／対象」の切替、選択区間の根拠を直下へ。比較元の名前と時刻は残し、時間軸だけを必要に応じて横スクロールさせます。一覧は続けて確認できる順に置きます。
- **既存スタックでの実装方針**：メディアクエリと表示切替で実装。画面全体の横溢れを防ぎ、時間軸のスクロール領域にラベルとフォーカスを付けます。動画2本の縦積みは避けます。
- **確認方法**：320・390・768 CSS px、200%ズーム、縦横向き、ソフトウェアキーボードで、映像・選択工程・確認操作の往復を実機検証。[WCAG Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

### R5：モード切替のARIAタブと実際の操作が一致しない

- **問題**：タブとしての意味付けに対し、矢印キー・パネル関連付けが不足しています。
- **根拠**：**操作・コード確認済み**。[analysis.html:38](../public/analysis.html#L38)、[fewshot.js:133](../public/fewshot.js#L133)。fewShotTab上のArrowRightで選択移動せず、click中心の実装です。`aria-controls` やroving tabindexの整理も必要です。
- **ユーザーへの影響**：支援技術が予告する操作と画面の挙動が一致しません。
- **重要度**：P2。
- **改善案**：タブとして実装を揃えるか、目的選択のボタングループ／ラジオとして扱います。独立モックでは `aria-pressed` のボタングループを使用しました。
- **既存スタックでの実装方針**：既存DOM・イベントを修正するだけで対応可能。モード変更時にファイル・語彙・設定を破棄しません。
- **確認方法**：キーボードのみで両モード選択、状態の読み上げ、設定保持を確認します。[APG Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

## 共通のデザイン評価

現行には、スキップリンク、ラベル、フォーカス表示、空検索の案内、原本保持、処理状態と回収状態の分離など、残すべき設計があります。無意味なグラデーションや装飾の多さが主問題ではありません。カード数を機械的に減らすより、**集計・動画・編集が同程度の重みで連続し、主作業が分かれた情報階層**を改善する方が効果的です。

モックはOlloの薄い区切り・白背景・青い選択色・動画中心の作業領域を採用。カード内にさらにカードを重ねることを避け、右側一覧は行形式にしました。「AIが優秀に見える」スコアや改善率を追加せず、観察内容と人の確認を区別しています。

## UX原則と対応する提案

- [Frame.io Comparison Viewer](https://help.frame.io/en/articles/9952618-comparison-viewer)：2つの対象を選んで比較に入り、並列表示・連動操作・対象へのフィードバックを扱う。T2の「比較対象を選んでから比較」、R1の並列配置、R2の同期説明に適用します。
- [NN/g Empty States](https://www.nngroup.com/articles/empty-state-interface-design/)：空状態を、状況と次の操作を伝える機会として使う。T1/T2の開始案内と、標準0本の表示に適用します。
- [NN/g Visibility of System Status](https://www.nngroup.com/articles/visibility-system-status/)：操作の応答と進行状況を理解できるようにする。R3の工程・状態別CTAに適用。取得できない完了率や残り時間は捏造しません。
- [WCAG Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)、[Status Messages](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)、[APG Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)：T3・R3・R4・R5の検証基準に使用します。今回の監査でWCAG総合適合を宣言するものではありません。

調査経路：agent-reachの検索・Web参照手順を利用。Exa検索は追加調査中にレート制限となったため、公式ページのJina Reader取得、Web検索、ブラウザでの公開画像確認を併用しました。検索結果だけの情報と画面を実見した情報を上表で分けています。

## モックと本体実装の境界

- [HTMLモック一覧](ui-audit-2026-09-21/index.html)は10画面です。開始2、結果2、処理中、完了、失敗、お手本ライブラリ、履歴、初回空状態を含みます。処理画面内で通信断・中止も切替できます。

- モックはAPI、実推論、外部フォント、リモート画像を利用しません。再生はSVGの模式映像を動かす操作例です。比較値・工程・日時・人物表記は架空です。

- 既存仕様との主な検討差分はプレイヤーの左右配置、目的別の結果表示、初回専用空状態、一覧と根拠の配置です。採用時に仕様と対応付けて更新してください。
